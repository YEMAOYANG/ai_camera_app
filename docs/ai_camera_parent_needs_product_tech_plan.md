# Mira Guardian（米拉） AI 智护摄像头家长需求与产品技术方案

编制日期：2026-05-19  
输入资料：家长需求访谈 Word、`research.md`、`xiaoban_v2_spec.md`、`ai_camera_test` Demo 代码、公开资料补充  
建议产品名：Mira Guardian（米拉）  
建议技术路线：Flutter 家长 App + Python AI 后端 + Kimi/MiniMax ModelRouter + 独立 ASR/TTS 语音链路 + 自有 AI 摄像头 + 端云混合架构

命名说明：Mira 是暂定品牌名，取“miracle / mirror / admirable”的联想，表达“看见、陪伴、守护和发现孩子成长细节”的方向；中文名“米拉”短、柔和、便于家长记忆。但正式命名可以继续迭代。无论品牌名最终叫什么，孩子日常唤醒摄像头的名字都不应被品牌名绑死，而应由孩子在首次使用时自己起名。

## 1. 执行摘要

这份文档把家长原始需求重新整理为一套可落地的产品与技术方案。当前家长最强的需求不是“多一个摄像头”，而是一个能够在孩子学习、生活、安全、作息和陪伴中承担一部分重复劳动的家庭 AI 助手。它要能看见孩子当前在做什么，也要能用亲切的语音与孩子互动，还要把过程整理成家长能快速理解的报告。

本产品的核心定位建议是：

> Mira Guardian（米拉）不是普通安防摄像头，也不是单纯学习机，而是一套“自有 AI 摄像头 + 家长 App + Python AI 后端”的家庭 AI 智护与成长中枢。它以家长规则为边界，以孩子成长场景为中心，覆盖安全、作息、习惯、陪伴、学习、家校任务和成长报告，帮助家庭减少反复催促、陪作业冲突和独处安全焦虑。

更直接地说，产品北极星是“解放家长”。家长不应该再靠一直盯着摄像头、盯着作业、盯着孩子吃饭睡觉来维持家庭秩序；米拉要把这些重复观察、温和提醒、证据收集和日报整理自动化。家长只在需要判断、确认、安抚、奖励或处理安全事件时介入。

AI 选型建议从“单一主模型”改为“按任务路由”。Kimi-K2.6 具备文本、图像、视频输入和较长上下文能力，适合摄像头画面理解、题目识别和复杂安全复核；MiniMax-M2.7 文本价格更低，适合普通对话、日报周报和后台摘要；MiniMax Speech 2.8 更适合承担 TTS、音色和声音复刻。DeepSeek 可作为文本问答或低成本兜底模型，但不建议承担视觉理解和摄像头多模态核心能力。语音链路要独立设计：ASR/TTS 由专门语音服务或设备端能力完成，避免把产品命脉押在单一模型供应商上。

建议第一阶段聚焦 6 个高价值闭环：

1. 作业陪伴：坐姿检测、专注提醒、离座提醒、题目引导式辅导。
2. 任务管理：把作息、学习、家务、打卡、小书包和睡前节点都统一成任务，默认创建到今天，也可安排到未来日期。
3. 任务执行：对具体任务做语音提醒、专注计时、完成判断、任务证据和家长确认。
4. 远程看护：家长 App 实时查看、音频通话、异常状态推送。
5. 安全守护：陌生人/敲门提醒、紧急呼救、家长晕倒或孩子无法表达时的异常检测。
6. 成长报告：任务完成、习惯表现、坐姿/专注/收纳/睡眠摘要、积分奖励。

在家长端 App 侧，第一版还应补上几个能显著提升信任感的闭环：任务证据与家长确认、奖励商店、摄像头语音兑换申请、睡眠与晨起基础卡片、安全事件处理、小书包和互动时长限制。它们都来自原始家长需求或成熟竞品启发，且能服务“少催促、可解释、家长可控”的主线。

当前 `ai_camera_test` 已经验证了很多关键能力：文本聊天、视觉问答、浏览器摄像头画面分析、坐姿/玩具/活动识别、语音唤醒、语音播报、MiniMax 音乐生成和今日报告雏形。短期可以用 TP-LINK 等支持 RTSP/ONVIF 的第三方摄像头做研发验证；但最终商业形态必须是用户购买自有品牌 Mira Guardian（米拉）摄像头，并下载米拉家长 App 完成配网、绑定、任务设置和日常使用。

### 1.1 最终产品形态

最终上线后，用户路径应该是：

1. 用户购买 Mira Guardian（米拉） AI 智护摄像头。
2. 下载米拉家长 App。
3. 用手机号登录或注册，并设置当前家长身份，例如妈妈、爸爸、祖辈或其他家人。
4. 用 App 扫描摄像头二维码或蓝牙发现设备。
5. 完成 Wi-Fi 配网、设备绑定和家庭成员授权。
6. 创建孩子档案，填写出生日期、就读阶段、班级/年级和作息等信息。
7. 进入摄像头首次引导：摄像头问孩子“我该怎么称呼你？”，再请孩子给摄像头起一个自己能记住、能说清楚的名字。
8. 设置任务、任务模板、专注计时、奖励规则、隐私模式和安全规则。
9. 摄像头在家庭场景中执行语音提醒、学习陪伴、安全告警和每日/每周报告。

第三方摄像头只作为研发脚手架，用来快速验证“看、听、说、提醒、报告、远程查看”这些体验能不能被家长接受；它不是最终商业交付方式，也不应该要求正式用户购买第三方摄像头。

### 1.2 首次使用与命名流程

孩子日常叫摄像头的名字不应由品牌强制决定。品牌名面向家长、渠道和售后；儿童唤醒名应该在首次使用时由孩子自己取，这样更容易记住、说清楚，也更容易建立亲近感。

推荐首次引导流程：

1. 家长下载米拉家长 App，完成注册、摄像头配网和家庭绑定。
2. App 提醒家长：“接下来请孩子一起完成命名，摄像头会问两个问题。”
3. 摄像头亮起柔和状态灯并说：“欢迎使用米拉 Guardian，我会帮你记录任务、提醒休息，也会在需要时通知爸爸妈妈。你能告诉我，我该怎么称呼你吗？”
4. 孩子回答自己的称呼，例如“小宇”“朵朵”“乐乐”。App 显示识别结果，家长可确认或修改。
5. 摄像头继续说：“那你也给我起一个名字吧。以后你叫这个名字，我就知道你在找我。”
6. 孩子给摄像头起名，例如“小豆”“阿布”“小贝”。摄像头复述：“好呀，以后你叫我小豆，我就会回答你。”
7. App 保存“孩子称呼”和“摄像头唤醒名”，并允许家长随时修改。

命名流程里的“互动边界”只做默认规则说明，不在首次使用里强迫家长配置。说明内容包括：作业模式只允许任务相关问答，睡前模式不主动开启长时间自由聊天，普通闲聊默认只保存主题摘要。真正的配置入口放在“我的 > 设备与规则 > 对话与人设”，家长之后可以调整自由聊天单次时长、每日总时长、睡前限制、作业模式限制和记录策略。

设计原则：

| 项目 | 原则 |
|---|---|
| 品牌名 | 可以正式、可信、适合家长购买决策 |
| 儿童唤醒名 | 必须短、好发音、孩子自己记得住 |
| 识别容错 | 支持近似发音、昵称变体和家长手动校正 |
| 家长控制 | 家长可修改唤醒名、关闭自由聊天、限制对话时长 |
| 隐私提示 | 首次录入前明确告知家长：称呼和语音样本用于设备唤醒与互动，不用于广告 |

### 1.3 超越学习机的产品边界

学习机已经很普及，Mira Guardian（米拉）不应该被定位为“又一个学习机”。学习机主要解决“孩子在屏幕里学什么”，而 Mira Guardian 要解决“孩子在真实家庭环境里如何安全、规律、专注、独立地成长”。

| 维度 | 普通学习机 | Mira Guardian（米拉） |
|---|---|---|
| 核心场景 | 屏幕内学习、题库、课程 | 真实家庭空间：书桌、卧室、客厅、门口、睡前、独自在家 |
| 交互方式 | 孩子盯屏幕操作 | 摄像头观察 + 语音陪伴 + 家长 App 设置规则 |
| 家长价值 | 看学习内容和学习时长 | 减少催促、远程看护、任务执行、安全告警、成长报告 |
| 覆盖年龄 | 多集中在学龄儿童 | 按年龄段和场景扩展，从幼儿看护到青少年自我管理 |
| 风险 | 增加屏幕时间 | 尽量减少孩子碰手机/平板，用语音和环境感知完成任务 |
| 数据 | 学习数据为主 | 学习 + 作息 + 安全 + 习惯 + 家校打卡 + 家庭协作 |

因此，Mira Guardian 的目标不是替代学习机，而是成为家庭中的“儿童 AI 智护与成长中枢”。学习只是其中一个重要模块，不能吞掉安全、作息、陪伴、家庭协作和成长记录这些更大的价值。

## 2. 资料来源与关键判断

### 2.1 内部资料

家长访谈 Word 文档里出现频率最高的关键词包括：作业、提醒、积分、报告、远程查看、安全、打卡、睡眠、陪玩、语音亲切度、防沉迷。当前仓库内的原始需求文件为 `docs/AI摄像头家长需求.docx`，其中新增强信号很明确：家长不仅要“看见孩子”，还希望 App 能管理学习缺漏、避免孩子对 AI 作业辅导形成依赖、审核打卡素材、记录睡眠和晨起、远程看护孩子独自在家的状态、处理吃饭拖拉、提醒第二天带书和物品、发起音频通话、判断作业中离座并提醒回座。产品侧应把“带书和物品”收敛为更适龄的“小书包”：幼儿园是入园物品，小学和初中才按课程表生成课本、练习册和学科材料。新增调研进一步强调：家长希望产品能自动整理孩子每天要做的事并监督执行；产品上不必单独创造另一套流程概念，可以统一收敛为“任务”：从某一天时间轴继续添加时自动带入该日期，从普通新建入口进入时必须先选择日期，家长也可以安排或修改未来日期任务。如果能和学而思网校等教育内容平台形成合作，把课程、作业和练习资源转换为任务模板，会更有吸引力；同时摄像头本身要有儿童愿意亲近的外观、人设和声音，不能只是一个冷冰冰的 AI 硬件。可以看出家长并不只是想“看见孩子”，而是想减少反复催促、减少陪作业冲突、减少安全担忧，同时保留家长的最终控制权。

`research.md` 的核心判断仍然成立：市场上儿童摄像头、AI 陪伴机器人、学习灯、安防摄像头各自存在，但“儿童陪伴 + 行为监督 + 家长报告 + 安全看护”的组合还没有形成成熟品类。现有机会来自这些赛道的交叉空白。

`ai_camera_test` 代码已经具备 Demo 级能力：

| 模块 | 当前能力 | 位置 |
|---|---|---|
| AI 对话 | 以 Kimi-K2.6 作为主模型，保留 Moonshot/OpenAI 兼容接口；DeepSeek 仅作为文本低成本兜底；儿童安全 System Prompt | `server.py` `/api/chat` |
| 视觉问答 | 上传当前画面，结合问题回答，可用于看题、看画面、读文字 | `server.py` `/api/vision_command` |
| 行为观察 | 分析画面中的活动、坐姿、玩具散落、置信度、提醒语 | `server.py` `/api/analyze_frame` |
| 语音输入 | Demo 阶段使用浏览器 Web Speech API 和 Whisper 兜底；产品化改为设备端音频流 + ASR | `static/index.html`、`server.py` `/api/speech` |
| 语音播报 | Demo 阶段使用浏览器 SpeechSynthesis；产品化改为设备端 TTS 或云端 TTS 推送到摄像头扬声器 | `static/index.html` |
| 今日报告 | 根据观察事件生成评分、技能维度、活动记录 | `server.py` `/api/report` |

## 3. 家长需求重新归类

### 3.1 一级痛点

| 痛点类别 | 家长真实表达 | 本质需求 | 产品机会 |
|---|---|---|---|
| 作业冲突 | “辅导孩子作业，不用每天鸡飞狗跳” | 家长想减少情绪消耗，又不想孩子没人管 | AI 作业陪伴与引导式辅导 |
| 拖拉与时间观念弱 | “到点自动唤醒”“吃饭太磨蹭” | 孩子缺少外部节奏，家长反复催促 | 任务提醒、任务模板、专注计时 |
| 不自觉与开小差 | “擦笔头”“离开座位”“有没有认真做” | 家长想知道孩子有没有进入任务状态 | 行为识别、专注提醒、离座提醒 |
| 学习缺漏 | “扫扫孩子，就知道学习缺漏并给计划” | 家长想知道短板在哪里，怎么补 | 错题/作业记录、知识点标签、个性化计划 |
| 安全焦虑 | “有人敲门不要开门”“妈妈晕倒通知爸爸” | 独处场景下需要主动告警和求助 | SOS、陌生人/敲门、跌倒/异常静止检测 |
| 家长可见 | “App 里看到做作业情况”“每天报告” | 家长想低成本掌握一天发生了什么 | 实时查看、事件流、日报周报 |
| 奖励激励 | “做家务得星星，表现不好扣分” | 家长需要正向激励工具 | 奖励规则、兑换、AI 自动记账 |
| 打卡作业 | “拍照录视频传到家长 App，不让孩子碰手机” | 家长想降低学校打卡负担并控屏 | 打卡拍摄、家长审核、一键转发 |
| 陪伴缺口 | “只有一个娃，天天需要陪玩” | 家长需要短时替代陪伴，但担心沉迷 | 受限时长的语音陪伴、故事、小游戏 |
| 睡眠作息 | “监测有没有睡觉，几点睡着，早上叫起床” | 家长想稳定作息并看到睡眠结果 | 夜间模式、睡眠判断、渐进闹铃 |
| 任务监督 | “帮你整理出孩子每天要做的事并监督执行” | 家长不想每天重新安排、重新催、重新核对 | 任务模板、任务序列、完成确认、漏项提醒 |
| 任务可信度 | “家长 App 可以看孩子做作业情况”“完成后自动传到家长 App” | 家长不只要结果，还要知道 AI 为什么判断完成 | 任务证据、截图/短视频、家长确认与纠错 |
| 奖励兑现 | “达到多少积分兑换奖品” | 积分要能落到真实奖励，而不是只显示数字 | 奖励商店、摄像头语音申请、家长审核、兑现记录 |
| 小书包 | “带书，明天的课程，要带哪些书” | 家长想减少早晨临时找书、漏带和幼儿园临时物品遗漏 | 小书包、前一晚/早晨提醒、临时物品、按学段生成 |
| 家庭协作 | “通知爸爸或其他亲属” | 多个照护人需要知道谁处理了什么 | 协作待办、处理人、处理状态、交接记录 |
| 内容吸引力不足 | “最好可以和学而思网校那些合作，把他们的东西也放进来，不然没有吸引力” | 家长需要学习资源和权威内容，不想再买一个孤立硬件 | 课程表导入、学习任务卡、合作内容、跳转/授权集成 |
| 儿童亲近感 | “狗狗猫猫对小朋友很有吸引力”“声音可以童趣一些” | 孩子是否愿意听，决定产品能不能长期使用 | 儿童友好 ID、原创角色声线、合法授权声包、趣味灯效 |

### 3.2 需求优先级建议

| 优先级 | 需求 | 原因 |
|---|---|---|
| P0 | 任务模板、任务提醒、专注计时、坐姿提醒、实时查看、语音对话、日报雏形 | 高频、明确、可验证、Demo 已有基础 |
| P0 | 引导式题目辅导、防直接答案、防沉迷、互动时长限制 | 直接回应家长最大担忧，决定信任感 |
| P0 | 任务证据、奖励兑换、睡眠基础卡片、安全事件处理、小书包 | 来自原始需求和竞品验证，适合放进家长端 MVP 增强闭环 |
| P1 | 积分系统、奖励商店、离座提醒、打卡拍摄、睡眠趋势、音频通话、儿童友好声线与外观 | 形成完整家庭闭环，提升留存和孩子接受度 |
| P1 | 紧急求助、陌生人/敲门提醒、家长异常通知、危险区域规则、成长时刻、家庭协作、作业依赖风险报告 | 安全和留存价值高，但要控制误报、隐私和监控感 |
| P2 | 学习缺漏诊断、个性化提分计划、多孩多设备、长期成长档案导出、学而思网校等教育内容合作、第三方班级小管家集成 | 价值高但实现复杂，依赖数据积累、内容版权和外部接口 |

## 4. 产品定位与设计原则

### 4.1 目标用户

目标用户不应被固定在 4-10 岁。Mira Guardian（米拉）的核心用户是“有儿童看护、作息、陪伴、学习和安全需求的家庭”，不同年龄段使用的功能重点不同。第一阶段可以优先验证学龄前到小学阶段的高频场景，但产品架构要支持更宽的儿童成长周期。

分龄价值建议：

| 年龄段 | 家庭主要痛点 | Mira Guardian（米拉）重点价值 |
|---|---|---|
| 0-3 岁 | 睡眠、哭声、独处风险、家长看护压力 | 睡眠/哭声辅助监测、异常声音、远程查看、家长突发状况告警 |
| 3-6 岁 | 作息建立、吃饭拖拉、收纳、安全意识、陪伴需求 | 生活提醒、睡前任务、收玩具、陌生人不开门、安全规则、故事陪伴 |
| 6-12 岁 | 作业、坐姿、专注、打卡、任务拖延、积分激励 | 专注计时、作业陪伴、引导式题目辅导、坐姿检测、打卡助手、日报周报 |
| 12 岁以上 | 自我管理、隐私边界、学习计划、亲子沟通 | 低打扰任务提醒、学习计划、周报摘要、家长协作，弱化监控感 |

孩子侧不建议只定位为“AI 老师”，而应定位为“有规则、会陪伴、懂边界的家庭 AI 助手”。低龄儿童可以把它当小伙伴，学龄儿童可以把它当任务陪伴者，年龄更大的孩子则需要更多隐私和自我管理空间。

家长侧的产品价值是“少催促、少争吵、少担心、有记录”。这比单纯“更聪明的 AI”更有付费理由。

### 4.2 产品边界

米拉应该做：

1. 执行家长预设的日程、任务、积分和安全规则。
2. 对孩子进行温和、短句、低频、可解释的提醒。
3. 引导孩子思考，而不是直接替孩子完成作业。
4. 把关键事件和趋势整理给家长。
5. 在紧急情况下尽快通知家长或预设联系人。

米拉不应该做：

1. 不应替代家长长期陪伴。
2. 不应鼓励孩子长时间和 AI 闲聊。
3. 不应收集不必要的隐私，例如学校、住址、电话、家庭收入等。
4. 不应绕过第三方学校 App 的规则自动提交内容。
5. 不应把“监控感”做得太强，避免孩子产生被审判感。

### 4.3 核心体验原则

| 原则 | 解释 | 具体做法 |
|---|---|---|
| 温柔但有边界 | 对孩子不吼、不羞辱、不比较，但能坚持规则 | 每次提醒 1-2 句，冷却期内不重复催促 |
| 家长可控 | 家长设规则，AI 执行与记录 | App 里配置任务、积分、对话时长、隐私模式 |
| 端侧优先 | 能在本地判断的尽量本地判断 | 坐姿、人形、唤醒词、基础事件本地处理 |
| 低打扰 | 少提醒、准提醒，不把孩子注意力拉走 | 多信号确认后提醒，提醒频次可调 |
| 可解释 | 家长知道为什么提醒、为什么扣分或加分 | 报告里记录触发原因和证据截图 |
| 不替孩子做 | 作业辅导采用提问式脚手架 | 分步骤引导、先问再提示、最后给思路 |
| 鼓励式教育 | 先看见孩子做对了什么，再提醒下一步 | 具体表扬行为，不贴标签、不比较、不恐吓 |
| 渐进放手 | 目标是让孩子少被催，而不是永远依赖提醒 | 稳定完成后降低提醒频率，转为仅记录或日报反馈 |

### 4.4 解放家长的产品闭环

米拉要解放的是家长的重复劳动，而不是取消家长的情感参与。产品闭环应从“家长盯着孩子做”变成“系统托管普通任务，家长处理关键节点”。

| 家庭负担 | 产品承担 | 家长保留 |
|---|---|---|
| 盯作业有没有开始 | 摄像头识别任务开始证据，低频提醒 | 只处理长期未开始或证据不清 |
| 反复催吃饭、洗漱、睡觉 | 任务模板 + 到点语音提醒 + 冷却期 | 设置规则和最终确认 |
| 陪玩和临时陪伴 | 限时故事、问答、小游戏、音乐 | 设定时长、禁用场景和亲子时间 |
| 检查家务和打卡 | 证据截图/短片 + 家长确认队列 | 批准、驳回、鼓励孩子 |
| 记录一天发生了什么 | 日报、周报、任务证据和异常摘要 | 看 30 秒结论，必要时追溯证据 |

这个闭环的衡量指标不应只是“孩子完成了多少任务”，还要看家长少花了多少盯守时间、孩子是否更能自启动、亲子冲突是否减少、孩子是否愿意继续听米拉提醒。

## 5. 产品功能方案

### 5.1 学习助手

#### 5.1.1 坐姿与用眼提醒

目标：降低家长对视力和坐姿的长期担忧。

功能流程：

1. 家长在 App 中开启学习模式。
2. 摄像头识别孩子是否在书桌区域。
3. MediaPipe Pose 或端侧模型判断头部、肩膀、身体前倾角度。
4. 连续异常超过阈值，例如 20-30 秒，触发温柔提醒。
5. 提醒后进入冷却期，例如 3-5 分钟，避免连续打扰。
6. 日报统计坐姿风险次数、改善趋势和高风险时段。

建议提醒语：

“小宝，把头轻轻抬高一点，眼睛离书本远一点。”

“我们坐直一点，写完这一小段就休息。”

#### 5.1.2 作业专注与离座提醒

目标：减少家长反复远程盯作业。

判断信号：

| 行为 | 视觉信号 | 时间信号 | 触发规则 |
|---|---|---|---|
| 写作业 | 桌面有书本/纸笔，手部书写，孩子在桌前 | 持续 2 分钟以上 | 进入学习状态 |
| 开小差 | 长时间低头玩物、视线离开桌面、无书写动作 | 超过 60-90 秒 | 轻提醒 |
| 离座 | 学习任务进行中，人离开书桌区域 | 超过家长设置的时间，如 3 分钟 | 呼唤回座 |
| 休息 | 专注计时休息阶段 | 休息时间内 | 不判定为开小差 |

关键是结合任务状态判断。孩子在休息时间离开，不应该被提醒；只有“任务正在进行”时才提醒。

#### 5.1.3 题目辅导

目标：孩子不会题时能获得帮助，但不养成“伸手要答案”的习惯。

推荐采用“三段式引导”：

1. 读题确认：先识别题目，若看不清就让孩子靠近镜头。
2. 提问引导：先问孩子这题考什么、第一步是什么。
3. 分层提示：最多给 2-3 个提示，再讲解思路，不直接报答案。

示例：

孩子：“小豆，这道题怎么做？”

小豆：“我先看看题目。它像是在考乘法关系。小宝先想一下，题目里哪些数字是一组？”

如果孩子不会：

“没关系，我们先找已知条件。你能指出题目里问的是总数、差值，还是每份数量吗？”

产品策略：

| 风险 | 设计控制 |
|---|---|
| 孩子直接要答案 | Prompt 强制先引导，不能第一轮给最终答案 |
| 题目识别不清 | 明确说没看清，不编造题目 |
| 孩子频繁问同类题 | 报告给家长：“本周乘法应用题提问 8 次” |
| 家长担心依赖 | App 中展示“引导过程”，而不是只展示答案 |

#### 5.1.4 AI 作业依赖防护

家长原始需求里明确担心“不会了就一直提问，然后都不动脑筋”。这个风险不能只靠 Prompt 说“不要直接给答案”，还要在家长 App 和策略层形成闭环。

建议策略：

| 风险信号 | 产品处理 |
|---|---|
| 同一题或同类题短时间反复求助 | 降低直接提示强度，先让孩子复述条件和第一步 |
| 孩子每道题都问 AI | 进入“少提示模式”，只给读题和思路，不连续讲解 |
| 孩子跳过思考直接问答案 | 摄像头回复“先说说你觉得第一步是什么”，并记录为依赖风险 |
| 一周内某类题高频求助 | 周报给家长展示“可能依赖 AI 求助”的标签和具体题型 |
| 家长希望强化独立完成 | App 可开启“作业模式：先思考 2 分钟再求助” |

家长端展示不应羞辱孩子，而应写成可行动建议，例如：“本周应用题求助 9 次，其中 5 次发生在读题后 30 秒内。建议明晚先让孩子圈关键词，再开启提示。”

#### 5.1.5 学习缺漏与提分计划

这是中长期能力，不建议 MVP 就承诺“扫一下就知道所有缺漏”。合理路径是：

1. P1：收集错题照片、AI 识别题型与知识点。
2. P1：生成“本周薄弱点”，例如计算粗心、应用题读题、拼音声调。
3. P2：结合年级、教材版本和学校考试目标，生成练习计划。
4. P2：与家长确认目标，例如“数学稳定到 90 分以上”，再安排每日 10-20 分钟专项训练。

要避免虚假承诺。AI 可以辅助发现模式，但不能凭单次扫描给出可靠完整诊断。

#### 5.1.6 AI 学习诊断与周报

`xiaoban_v2_spec.md` 中提出的“AI 老师诊断”方向很有价值，可以作为 Mira Guardian（米拉）的中高阶差异化能力：普通摄像头只能看见孩子在不在，学习机通常只能处理屏幕内题目，而米拉可以长期观察“任务、题目、卡顿、提问、错题、坐姿、专注”这些家庭真实学习数据，再给家长一份结构化学习反馈。

建议把它设计成“长期诊断”，而不是“扫一眼定终身”。核心输入包括：

| 输入数据 | 来源 | 用途 |
|---|---|---|
| 题目问答记录 | 孩子举题给摄像头、视觉模型读题 | 判断孩子常问的题型和知识点 |
| 错题照片 | 打卡/作业辅导时拍摄 | 归类错因，例如审题、计算、概念不清 |
| 任务完成数据 | 专注计时和任务记录 | 判断学习节奏、拖延和独立完成情况 |
| 专注/离座记录 | 摄像头行为状态机 | 判断学习习惯和环境干扰 |
| 坐姿/休息记录 | 端侧姿态检测 | 关联用眼、疲劳和学习效率 |

输出给家长的报告可以包括：

| 模块 | 内容 |
|---|---|
| 薄弱点热力图 | 按学科、题型、知识点标记“已掌握、需加强、薄弱” |
| 错题归因 | 说明同类错误是否反复出现，例如进位加法、应用题读题、看图写话表达 |
| 进步曲线 | 对比本周与上周的坐姿、按时率、错题率、独立完成率 |
| 下周提升计划 | 给出每天 10-20 分钟的可执行练习安排 |
| 家长协助建议 | 告诉家长今晚只需要关注哪 1-2 个点，减少盲目加练 |

学习诊断必须遵守三个边界：

1. 不宣称替代老师或专业测评。
2. 不直接承诺“保证提到 90 分”。
3. 不根据单次作业做结论，至少基于一周或多次样本形成趋势。

### 5.2 时间管家

这是家长需求里最强、最容易落地、最适合摄像头语音形态的模块。

#### 5.2.1 任务

App 中只保留“任务”一个核心概念。家长从某一天的任务时间轴继续添加时，系统默认带入当前选中的日期；从普通新建入口进入时，不默认日期，必须先选择今天、明天、某个未来日期或重复规则。到日期后，未来任务自动进入当天任务列表。

家长在 Flutter App 中设置：

| 字段 | 示例 |
|---|---|
| 日期/重复 | 时间轴进入默认选中日期；普通新建需先选今天、明天、指定日期或重复规则 |
| 任务名称 | 数学作业 |
| 任务类型 | 学习、家务、吃饭、洗澡、睡眠、打卡 |
| 时长 | 25 分钟 |
| 休息 | 5 分钟 |
| 积分 | 完成 +5 |
| 检测方式 | 手动确认、AI 判断、家长确认 |
| 提醒方式 | 语音、App 推送、灯光 |
| 模板来源 | 手动创建、系统推荐、家长自定义模板 |

任务提醒语不应成为家长必填字段。家长只需要设置“做什么、什么时候做、做多久、完成后多少积分”；具体怎么提醒孩子，应由 AI 根据孩子称呼、任务类型、当前状态和提醒次数自动生成。这样可以避免家长为了一个任务还要写多句话术，也能保证提醒语始终符合“不批评、不贴标签、给一个小动作”的产品语气。

#### 5.2.1.1 孩子档案驱动的任务模板

录入孩子档案时，必须收集出生日期、就读阶段和班级/年级。年龄由 App 根据出生日期自动推算，不让家长手动估算。就读阶段至少包括：

| 就读阶段 | 班级/年级选项 | 模板生成重点 |
|---|---|---|
| 幼儿园 | 小班、中班、大班 | 作息、生活自理、收纳、安全、亲子阅读 |
| 小学 | 一至六年级 | 作业习惯、阅读、小书包、运动、家务 |
| 初中 | 七至九年级 | 自主计划、作业专注、错题复盘、运动、屏幕边界 |
| 其他 | 家长自定义 | 只推荐通用生活、安全和作息任务 |

App 交互必须保持表单职责清晰：出生日期使用日期选择器，就读阶段和年级都使用下拉选择；就读阶段包括幼儿园、小学、初中，年级随学段切换，班级名称允许手动输入。孩子档案页不展示“作息建议”“专注建议”这类中间参数，这些参数应在任务模板、提醒策略和小书包规则里自动体现。孩子档案页面还要区分入口来源：首次绑定流程进入时，底部继续引导“命名摄像头”；从“我的”进入时只作为资料编辑页，不再显示 onboarding CTA。

外部依据可以转化为模板规则：教育部作业管理要求小学一二年级不布置书面家庭作业，小学其他年级书面作业平均不超过 60 分钟，初中不超过 90 分钟；睡眠管理要求小学生、初中生、高中生每天分别达到 10、9、8 小时睡眠。CDC 的家庭结构建议强调稳定、可预测的 routine；奖励建议强调具体、适龄、正向的行为目标。国家体育总局也建议儿童青少年运动遵循趣味、安全、有效原则，并给出耐力、力量等练习频率建议。因此米拉任务模板不应只围绕作业，还要覆盖睡眠、运动、收纳、生活自理和安全边界。

系统推荐模板：

| 阶段 | 模板方向 | 示例任务 |
|---|---|---|
| 幼儿园小/中班 | 作息、生活自理、收纳、安全 | 起床穿衣、吃饭、收玩具、睡前洗漱、亲子阅读、陌生人不开门 |
| 幼儿园大班 | 入学准备、规则感、简单家务 | 检查小书包、练习握笔、图书阅读、准备第二天物品、睡前洗漱 |
| 小学一二年级 | 作业习惯、阅读、小书包整理 | 读书 15 分钟、口算练习、检查小书包、按时睡觉 |
| 小学三至六年级 | 专注学习、运动、家务、错题 | 作业专注 25 分钟、错题订正、英语朗读、运动 30 分钟、整理房间 |
| 初中 | 自主计划、复盘、运动、屏幕边界 | 作业 45 分钟、错题复盘、明日计划、运动、手机/平板收纳 |

任务模板参考依据：

| 来源 | 可转化为产品规则 |
|---|---|
| [教育部《义务教育学校作业管理》](https://hudong.moe.gov.cn/srcsite/A06/s3321/202104/t20210425_528077.html) | 小学一二年级不默认生成书面家庭作业模板；小学三至六年级、初中学习任务默认时长要控制在合理范围内 |
| [教育部中小学生睡眠管理](https://news.cctv.com/2021/04/03/ARTIVn1HVuZ9iMS3juLu2miK210403.shtml) | 小学和初中任务模板要优先保护就寝时间，晚间任务到点未完成时应提示家长按时就寝 |
| [CDC 家庭结构与 routine 建议](https://www.cdc.gov/parenting-toddlers/structure-rules/structure.html) | 幼儿园和小学低年级任务模板要稳定、可预测，围绕早晨、吃饭、睡前等固定场景 |
| [CDC 儿童健康 routine 与运动建议](https://www.cdc.gov/healthy-weight-growth/tips-parents-caregivers/) | 任务模板不能只围绕学习，应默认包含运动、睡眠、饮食和屏幕边界 |
| [CDC 奖励建议](https://www.cdc.gov/parenting-toddlers/discipline-consequences/using-rewards.html) / [AAP 正向奖励建议](https://www.healthychildren.org/English/family-life/family-dynamics/Pages/Positive-Reinforcement-Through-Rewards.aspx) | 奖励任务要具体、适龄、正向，不把扣分作为默认手段 |
| [CDC 青少年独立性建议](https://www.cdc.gov/parenting-teens/tips-encouraging-independence/index.html) | 初中阶段要给孩子更多自主空间，任务提醒应低打扰、可协商、尊重隐私 |

任务模板生成原则：

1. 先按年龄和就读阶段推荐，不要求家长从空白页开始。
2. 模板默认保守，家长可增删改；系统不自动给孩子加压。
3. 学习任务时长要遵守减负和睡眠边界，不建议默认生成过量学习任务。
4. 提醒话术随年龄变化：幼儿园更短、更具体、更像陪伴；小学强调步骤和鼓励；初中强调尊重、自主和低打扰。
5. 模板可包括日期规则，例如“周一至周五”“明天早晨”“每周三运动”“考试周临时模板”。

任务系统的教育目标不是“让孩子永远被提醒”，而是让孩子逐渐少被提醒。每个重复任务都应记录三个指标：是否按时开始、需要提醒几次、是否能独立完成。连续稳定后，App 可以建议家长降低提醒频率或把任务改为仅记录，让孩子获得更多自主感。

#### 5.2.2 专注计时

推荐默认节奏：

1. 学习 25 分钟。
2. 休息 5 分钟。
3. 每完成 2-3 轮安排长休息。
4. 低龄儿童可支持 15/5 或 20/5。

语音流程：

“小宝，我们第一项是数学作业，计时开始。”

“数学时间到了，休息 5 分钟。可以喝水、走一走。”

“休息结束了，我们开始语文作业。”

设计重点：

| 问题 | 方案 |
|---|---|
| 孩子拖延开始 | 任务开始前 3 分钟预提醒，到点正式开始 |
| 孩子要求延长休息 | 可以语音申请一次，家长可设置是否允许 |
| 孩子没完成 | 标记为“超时未完成”，不直接批评，报告给家长 |
| 任务临时变化 | 家长 App 一键暂停、跳过、延后 |

#### 5.2.3 任务拖拉与未开始处理

单纯“到点提醒”不够，因为真实家庭里更常见的是：到了 9:00 该读书，孩子听到了但没有坐到桌前，或者一直拖到家长继续催。产品需要把“未开始”当成明确状态处理，而不是无限重复播报。

默认状态机：

| 状态 | 含义 | 处理 |
|---|---|---|
| `scheduled` | 已计划，还未提醒 | 等待提前提醒或到点 |
| `pre_reminded` | 已提前提醒 | 到开始时间后正式提醒 |
| `due` | 已到点 | 播报正式提醒，进入宽限期 |
| `pending_start` | 到点后仍未确认开始 | 给第一句很小的行动提醒 |
| `delayed` | 已多次提醒仍未开始 | 降低频率，继续一次具体提醒 |
| `needs_parent_attention` | 超过最大提醒次数 | 停止反复催促，交给家长处理 |
| `running` | 已开始 | 按任务规则观察坐姿、离座、进度 |
| `completed` / `expired` / `skipped` | 已完成、超时或跳过 | 写入报告和奖励计量流水 |

默认提醒节奏：

1. T-3 分钟预提醒：“小宝，3 分钟后要读书啦。”
2. T 到点正式提醒：“小宝，现在到读书时间啦，我们先把书拿到桌上。”
3. 宽限期默认 5 分钟，期间不反复打扰。
4. 宽限期后如果没有开始迹象，进入 `pending_start`，只给一个小动作：“先把书本和文具放到桌上。”
5. 第二次提醒更具体：“读第一页就算开始，不用一下子读完。”
6. 超过家长设置的最大提醒次数后，进入 `needs_parent_attention`，停止反复催促，并在家长 App 首页显示“需要处理”。

开始证据需要和任务类型绑定：

| 任务类型 | 可接受开始证据 | 不确定时 |
|---|---|---|
| 读书/作业 | 孩子在桌前，书本/纸笔可见，阅读/书写姿态稳定，或单次高置信视觉判断已经达到阈值 | 标记“证据不足”，继续观察，不把“坐在镜头前”直接当成开始 |
| 吃饭 | 餐桌/餐具/用餐姿态可见，或孩子坐到餐桌且出现进食动作 | 不强行判断，继续观察 |
| 玩具整理 | 孩子在收纳区执行收纳动作，或玩具散落状态出现持续改善 | 交给家长兜底确认 |
| 打卡 | 素材已采集，家长审核通过 | 不自动提交第三方平台 |

读书任务不能只用“孩子坐在摄像头前”判定开始。后端任务 worker 到点后必须读取 monitor 最近视觉观察，融合 `has_person`、`activity`、`homework_like`、`confidence`、`activity_stability`、画面描述中的书本/纸笔/桌前证据后，才自动把任务置为 `running`。如果只看到孩子坐着，但没有书本、纸笔、阅读或书写证据，则保持 `due/pending_start`，给“小动作”提醒；如果视觉证据不足，则显示原因并继续观察。家长 App 或 HTML 测试台里的“开始”按钮只能作为异常兜底，不是主流程。

积分策略：按时开始和完成可自动加分；严重拖拉或拒绝任务只生成“家长确认扣分”事件，不默认自动扣分，避免 AI 因误判惩罚孩子。

当前 HTML 测试台需要同步展示：当前任务状态、宽限倒计时、拖拉提醒次数、下一次提醒时间、AI 观察证据、以及“延后 5 分钟 / 兜底确认开始 / 提醒一次 / 跳过 / 完成”按钮。真实提醒和开始判定由后端任务 worker 与 monitor runtime 完成，不依赖 HTML 页面开着。

#### 5.2.4 生活提醒

适合高频家庭场景：

1. 吃饭限时提醒：避免一顿饭拖太久。
2. 睡前任务：收玩具、洗漱、读故事、关灯。
3. 起床闹铃：渐进式唤醒，不一上来大声叫。
4. 小书包：按学段提醒水杯、备用衣物、课本、画具、运动服等需要带去学校或幼儿园的物品。
5. 家务任务：收玩具、整理房间、擦桌子。

#### 5.2.5 任务模板库

新增调研里“帮你整理出孩子每天要做的事并监督执行”非常关键，但家长端不要再出现独立的流程概念。正确落点是任务模板库：系统根据孩子档案生成一组默认任务，家长选择启用即可。

任务模板分类：

| 分类 | 作用 | 典型任务 |
|---|---|---|
| 作息任务 | 稳定起床、吃饭、午休、睡前和就寝 | 起床、早餐、午休、睡前洗漱、关灯睡觉 |
| 学习任务 | 支持作业、阅读、朗读、错题复盘 | 数学作业、阅读 15 分钟、英语朗读、错题订正 |
| 生活自理 | 培养收纳、整理、个人卫生 | 检查小书包、收玩具、整理房间、准备衣物 |
| 家务任务 | 鼓励家庭责任感 | 摆碗筷、擦桌子、倒垃圾、给植物浇水 |
| 运动任务 | 保护视力、睡眠和情绪状态 | 户外运动、跳绳、拉伸、球类活动 |
| 安全任务 | 强化独处和门口等高风险场景 | 陌生人不开门、厨房/阳台提醒、SOS 练习 |
| 打卡任务 | 帮家长收集学校或兴趣班需要的素材 | 朗读打卡、体育打卡、手工作品拍照 |

日期和展示规则：

1. 所有模板启用后都生成任务，不生成第二套对象。
2. 从某一天时间轴继续添加时默认带入该日期；普通新建入口必须先选择日期，家长可选今天、明天、未来日期或重复规则。
3. 首页只显示当前任务、下一项任务、异常卡住任务和待处理确认。
4. 任务页提供“今天 / 明天 / 本周 / 日历”视图。
5. 报告页按任务类型汇总完成情况、证据、积分和卡点。

这个模块是产品超越学习机的重要抓手。学习机通常只覆盖“学习内容”，而任务模板库覆盖真实家庭生活，把学习、作息、家务、打卡和睡眠连接成一个可执行的任务系统。对家长可见的信息应该是孩子状态和下一项任务，不应把任务数量或完成率放到首页主视觉里。

#### 5.2.6 睡眠与晨起管理

原始需求里“监测有没有在睡觉，几点睡着的，早上可以闹铃叫起床”很明确。这个能力应优先在家长 App 里做成基础卡片和日报摘要，不要一开始包装成医疗级睡眠监测。

首版能力：

| 模块 | 家长 App 展示 | 处理原则 |
|---|---|---|
| 睡前任务 | 洗漱、检查小书包、上床、关灯等任务项 | 按任务节点确认，不制造睡眠焦虑 |
| 入睡记录 | 上床时间、疑似入睡时间、长时间未睡提醒 | 只标记“疑似”，避免绝对判断 |
| 夜间事件 | 夜醒、哭声、异常声音、离床 | 只保存必要事件和短片 |
| 晨起闹铃 | 待响、已响、已延后、已起床 | 支持渐进提醒和家长确认 |
| 睡眠日报 | 入睡时长、夜醒次数、起床时间、趋势 | 给家长可行动建议，不做诊断 |

睡眠场景要默认进入低打扰模式：夜间不推送普通提醒，不主动开启闲聊，只保留安全事件、异常声音、家长主动通话和晨起闹铃。

#### 5.2.7 小书包

“小书包”承接家长说的“明天的课程要带哪些书”，但不能只理解成带课本。不同学段的真实准备方式不同：幼儿园不默认带书，主要是入园物品；小学和初中才可能根据课程表准备课本、练习册、作业本和学科材料。这个模块不需要复杂 AI 也能带来明显价值，关键是避免早晨临时找东西、漏带材料和孩子书包过重。

推荐流程：

1. 家长在孩子档案里选择书本/物品处理方式：大部分放家里、部分放学校、有储物柜、书包留校、只按老师通知准备。
2. 幼儿园模板默认生成水杯、备用衣物、园服、午睡用品、活动材料、通知回执等入园物品，不生成课本清单。
3. 小学和初中模板可录入或导入课程表，每门课绑定常用物品，例如课本、练习册、作业本、运动服、画具、手工作品。
4. App 前一晚生成“小书包”，只提醒第二天真正需要带的东西。
5. 摄像头在睡前任务或早晨流程中提醒孩子检查小书包。
6. 家长 App 显示已准备、未准备、家长手动确认。

页面交互也要按学段变化：幼儿园用“入园物品”清单和“按老师通知 / 每日固定 / 临时活动”规则；小学用“课程表准备”清单和“部分书放学校 / 每天带回 / 有储物柜”规则；初中用“自主清单”和“只带明日 / 有储物柜 / 按老师通知”规则。这样家长不会在幼儿园阶段看到不相关的课本操作，也能让小学、初中场景保留真实的书本和资料管理差异。

这些规则不是展示标签，而是影响清单生成和提醒策略：

| 学段 | 规则 | 产品作用 |
|---|---|---|
| 幼儿园 | 按老师通知 | 只把老师通知、园所群消息和临时活动变成清单，避免每天出现无关物品 |
| 幼儿园 | 每日固定 | 每天固定提醒水杯、备用衣物、园服和午睡用品 |
| 幼儿园 | 临时活动 | 平时少提醒，遇到手工、春游、运动会等活动时重点生成材料清单 |
| 小学 | 部分书放学校 | 不把留校课本加入晚间清单，只提醒需要带回家的作业本、练习册和临时材料 |
| 小学 | 每天带回 | 每天晚间检查课本、作业本和文具，适合学校要求书本每天带回的情况 |
| 小学 | 有储物柜 | 把清单分成“柜内保留”和“明天带回”，只在需要补充或带走时提醒 |
| 初中 | 只带明日 | 只按第二天课表生成学科资料，减少书包重量和家长逐项检查 |
| 初中 | 有储物柜 | 默认把常用资料留在学校，只提醒错题本、作业材料和需要带回签字的内容 |
| 初中 | 按老师通知 | 不强依赖课程表，主要根据老师通知、作业要求和临时活动生成清单 |

首版可以手动维护小书包；P1 再支持截图识别课程表或老师通知；P2 再考虑和学校或教育平台同步。这个功能的目标不是鼓励孩子多带，而是让孩子少漏带、少多带，并逐步养成自我整理习惯。

#### 5.2.8 任务证据、家长确认与纠错

家长端不能只展示“AI 判断已完成”。对作业、家务、打卡、睡前任务这类任务，App 需要给出可解释证据，让家长能确认或纠错。

证据类型：

| 任务 | 证据 | 家长操作 |
|---|---|---|
| 作业 | 开始时间、专注轮次、桌面截图、离座次数、求助摘要 | 确认完成、部分完成、驳回 |
| 家务 | 整理前后截图、短视频片段 | 确认加分、撤销加分 |
| 打卡 | 照片/视频素材、拍摄时间 | 审核、保存、分享 |
| 睡前任务 | 任务节点、上床时间、关灯时间 | 确认完成、改为跳过 |
| 小书包 | 物品勾选、家长确认 | 标记已准备或漏带 |

纠错结果要进入报告和奖励计量流水。例如 AI 自动加分后，家长可以撤销并标记“证据不足”；AI 判断未完成时，家长也可以手动确认，避免孩子被误判惩罚。

### 5.3 安全卫士

安全模块价值很高，但必须降低误报和责任风险。建议按“提醒、通知、呼救”三级设计。

#### 5.3.1 孩子独自在家

典型场景：

1. 有人敲门。
2. 门口有人徘徊。
3. 孩子靠近门口或准备开门。
4. 孩子喊“救命”“帮我打电话给爸爸”。

产品流程：

1. 摄像头或门口设备识别敲门声/门铃/人形。
2. 室内摄像头提醒孩子：“小宝，不要开门，等爸爸妈妈确认。”
3. App 推送给家长，附短视频或截图。
4. 家长一键音频通话。

#### 5.3.2 紧急求助

语音触发关键词：

| 类别 | 关键词 |
|---|---|
| 呼救 | 小豆救命、帮我打电话、我害怕 |
| 家长异常 | 妈妈晕倒了、爸爸摔倒了、叫不醒 |
| 危险 | 着火了、冒烟了、有人闯进来、流血了 |

触发后流程：

1. 立即停止普通对话和任务提醒。
2. 用一句话确认：“我马上通知爸爸妈妈，你先离危险远一点。”
3. 推送 App、短信或电话给紧急联系人。
4. 上传最近 10-30 秒音视频片段，供家长判断。
5. 在家长未响应时，升级通知第二联系人。

#### 5.3.3 幼童无法说话或表达不清

可逐步加入：

1. 跌倒检测：人体高度骤降、姿态异常、碰撞声。
2. 异常静止：成年人或孩子长时间倒地/趴地不动。
3. 异常声音：尖叫、哭声、玻璃破碎、烟雾报警器声。
4. 危险区域：阳台、厨房、窗边、插座附近的虚拟围栏。

这类能力必须在 App 中标注“辅助提醒，不替代监护”，并允许家长调节敏感度。

#### 5.3.4 安全区域与事件处理

竞品里的“危险区域/安全区域”能力对家庭看护有借鉴价值，但米拉不能把它做成全天高压监控。建议家长 App 允许家长配置少量高风险区域，并把事件处理流程做清楚。

推荐安全区域：

| 区域 | 风险 | 处理 |
|---|---|---|
| 门口 | 陌生人、孩子开门 | 语音提醒孩子远离门，App 推送家长 |
| 厨房 | 火、电、刀具、热水 | 低龄儿童进入时提醒并通知家长 |
| 窗边/阳台 | 攀爬、跌落 | 高优先级告警，保留短片 |
| 楼梯 | 跌倒 | 低龄儿童或夜间进入时提醒 |
| 插座/危险物品区 | 触电或误拿 | 家长自定义区域，按敏感度提醒 |

家长 App 的安全事件详情需要展示：事件类型、发生时间、区域、截图/音频/短视频、处理人、处理状态、是否误报、是否已通知第二联系人。处理状态建议是 `待处理`、`已联系`、`已解决`、`误报`，避免家长收到推送后不知道谁在处理。

### 5.4 家长 App 与远程看护

Flutter 家长 App 是产品信任的核心。原型反馈说明首页不应只是“今日任务 + 功能入口 + 进度数字”。家长打开 App 的第一秒，最想知道的是孩子现在是否正常、是否需要自己处理。建议首页回答三个问题：

1. 孩子现在在哪里、在做什么、状态是否正常？
2. 接下来最需要关注的一件事是什么？
3. 有没有需要我处理的异常或确认？

核心页面：

| 页面 | 内容 |
|---|---|
| 首页 | 孩子当前状态、当前任务、下一步提醒、风险与异常、待处理事项、实时看护入口 |
| 实时看护 | WebRTC 视频、音频通话、云台控制、截图 |
| 任务 | 今天、明天、本周、日历、任务模板、任务详情、小书包 |
| 任务详情 | 专注计时、任务证据、提醒记录、完成确认、误判纠错、积分 |
| 睡眠 | 睡前任务、入睡/起床记录、夜间事件、晨起闹铃 |
| 我的 | 当前家长资料、账号安全、家庭账户、订阅、报告、积分奖励、打卡审核、成长时刻、家庭协作、成员权限、人设、语音、隐私、设备管理 |

远程看护要注意隐私模式：

1. 家长查看时设备端亮灯或语音提示。
2. 孩子可看到摄像头处于工作状态。
3. 家长可设置“学习时仅事件截图，不连续录像”。
4. 支持物理遮挡或电子隐私模式。

首页主视觉建议是一张“孩子状态卡”，而不是任务进度条。状态卡应包含：孩子所在区域、正在做的事、当前任务、下一步、设备/隐私状态、是否有安全风险。任务进度可以通过二级入口查看，或在日报里汇总；首页只保留对即时决策有帮助的信息。

家庭协作要作为家长 App 的基础能力，而不是后期运营补丁。安全事件、打卡审核、任务纠错、奖励兑换都需要记录处理人和处理状态；多家庭成员协作时，爸爸、妈妈、祖辈或其他家人看到的信息和权限可以不同。默认只有监护人能看完整报告和对话摘要，临时查看者只看到与当天任务、安全和待办相关的最小必要信息。

### 5.5 每日报告与成长记录

日报不是流水账，要让家长 30 秒看完。

日报结构建议：

1. 今日摘要：完成了什么、哪里需要家长关注。
2. 任务完成：早晨、放学后、作业、家务、睡前等关键任务完成情况。
3. 任务进度：完成/未完成/超时。
4. 任务证据：关键任务的截图/短片、家长确认和纠错记录。
5. 行为习惯：坐姿、专注、收纳、作息。
6. 睡眠与晨起：疑似入睡时间、夜醒、起床、晨起闹铃。
7. 关键事件：提醒记录、异常记录、照片精选。
8. 成长时刻：当天值得保留的积极片段。
9. 明日建议：最多 1-3 条可执行建议。

周报结构建议：

1. 学习诊断：本周高频提问题型、薄弱知识点、错题归因。
2. 习惯趋势：坐姿、专注、按时开始、离座、收纳、睡眠。
3. 作业依赖风险：是否频繁问同类题、是否跳过思考直接求助。
4. 进步曲线：和上周相比哪些指标改善、哪些指标变差。
5. 家庭协作：本周哪些待办由谁处理，是否存在长期未处理事项。
6. 下周计划：最多 3 个重点目标，不把家长推入无穷加练。
7. 推荐资源：练习页、教材页码、亲子讲解建议，可由家长确认后使用。

示例：

| 维度 | 指标 |
|---|---|
| 学习 | 学习总时长、专注计时完成轮数、离座次数 |
| 学习诊断 | 高频提问题型、薄弱知识点、错题归因、下周提升建议 |
| 任务 | 小书包、放学后切换、作业、家务、睡前任务完成情况 |
| 坐姿 | 坐姿提醒次数、最长连续规范时长 |
| 时间管理 | 按时开始任务数、拖延任务数 |
| 生活习惯 | 收纳完成、吃饭用时、睡觉时间 |
| 安全 | 异常事件、家长查看次数、SOS 记录 |
| 陪伴 | 对话时长、故事次数、小游戏次数 |
| 睡眠 | 上床时间、疑似入睡时间、夜醒次数、晨起状态 |
| 任务证据 | 自动判断次数、家长确认次数、纠错次数 |
| 成长时刻 | 独立完成、连续专注、主动收纳、睡前任务完成等精选片段 |
| 协作 | 待处理事项数量、处理人、处理时长 |

成长时刻不是营销相册，而是家长能回看和鼓励孩子的轻量记录。默认只保留精选片段和家长收藏内容，不保存全天录像。典型成长时刻包括：第一次独立完成一项任务、连续专注两轮、主动回到座位、自己收好玩具、睡前任务完整完成。家长可以收藏、删除、隐藏或分享，但普通家庭成员不默认拥有全部查看权限。

#### 5.5.1 儿童对话记录是否给家长看

建议记录，但不要做成“家长实时偷看孩子全部聊天”的产品。更合适的设计是：默认给家长看每日对话摘要和风险片段，逐字记录需要家长明确开启，并且在 App 和设备端有清晰提示。

这样做的理由：

1. 家长需要知道孩子每天和 AI 说了什么大方向，尤其是作业求助、情绪低落、陌生人、安全求助、身体不舒服等内容。
2. 儿童产品必须保护孩子的心理空间。如果所有闲聊都默认逐字展示，孩子会觉得自己一直被审问，长期会降低信任。
3. 对话记录是产品改进、家长理解孩子和安全追溯的重要材料，但必须遵守最小必要、可删除、可关闭的原则。

推荐分级记录策略：

| 记录类型 | 默认策略 | 家长端展示 | 保存周期 |
|---|---|---|---|
| 普通闲聊 | 只保存摘要 | “今天聊了恐龙、画画和周末计划，共 6 分钟” | 默认 7-30 天，可关闭 |
| 作业辅导 | 保存题目、引导步骤和结果摘要 | 展示孩子问了什么题、AI 如何引导、是否直接给答案 | 默认 30-90 天 |
| 情绪表达 | 保存摘要，必要时标记关注 | “孩子提到今天不太开心，原因可能和同学有关” | 默认 30 天 |
| 安全/异常 | 保存逐字内容、音频片段和事件前后截图 | 作为紧急事件展示，便于家长判断 | 默认 90 天，可手动延长 |
| 家长主动通话 | 按通话记录保存元数据 | 时间、时长、是否有截图/录制 | 按家长设置 |

家长 App 展示建议：

1. 日报中加入“今日对话摘要”，不把逐字内容塞进日报首页。
2. 支持按标签筛选：学习、情绪、安全、生活、闲聊。
3. 对普通闲聊只展示摘要和时长；对安全事件展示原文和音频证据。
4. 家长可以一键删除某天对话记录，也可以关闭普通聊天记录。
5. 家长开启“逐字记录”时，App 要明确说明用途，并在设备端用灯效或提示音表达当前处于记录模式。

儿童侧话术要自然，不要像审讯：

“我会把今天重要的事情整理给爸爸妈妈，比如作业卡在哪里、有没有需要帮忙的地方。普通聊天我只记一个小摘要。”

“如果你说到受伤、害怕或者需要找爸爸妈妈，我会马上帮你通知他们。”

### 5.6 积分奖惩系统

积分系统要做成家长工具，不要做成游戏化诱导沉迷。

规则建议：

| 行为 | 默认积分 | 审核方式 |
|---|---:|---|
| 按时开始任务 | +1 | AI 自动 |
| 完成一项作业 | +5 | 家长确认或 AI 辅助 |
| 坐姿规范 25 分钟 | +2 | AI 自动，上限每日 6 分 |
| 收好玩具 | +3 | AI 判断后家长可撤销 |
| 完成打卡 | +3 | 家长确认 |
| 超时严重或拒绝任务 | -1 至 -3 | 家长手动 |

原则：

1. 少扣分，多正向强化。
2. AI 自动加分可撤销，扣分默认家长确认。
3. 奖励计量类型和兑换规则由家长设置，不由 AI 擅自承诺；达到阶段阈值只提醒家长，不自动清零或自动发奖。
4. 语音反馈要具体：“刚才你自己回到座位了，加 1 颗星。”
5. 不建议随意扣回孩子已经获得的积分；严重问题优先进入家长确认和沟通。

奖励商店建议作为 P0/P1 之间的增强闭环。奖励计量如果不能兑换真实奖励，很容易变成冷冰冰的数字；但奖励商店也不能诱导孩子沉迷。家长 App 中建议支持：

| 功能 | 说明 |
|---|---|
| 计量类型 | 家长选择使用积分、小红花或小星星，默认是积分；三者是互斥计量方式，不能互相换算 |
| 阶段阈值 | 家长设置多少个单位算一个阶段，默认 10，可调整；例如 10 积分、10 朵小红花或 10 颗小星星达到后提醒“已积满” |
| 继续累积 | 达到阈值后家长可以不兑换，选择继续累积到更大的奖励；奖励计量不自动清零 |
| 奖品设置 | 家长自定义奖品名称、所需数量、有效期、每日/每周兑换限制；已添加奖品可右滑修改或删除 |
| 家长主动兑换 | 不管孩子有没有申请，家长都可以主动选择奖品兑换；确认后扣除对应数量，记录兑换前后余额 |
| 语音兑换申请 | 孩子可对摄像头说“我想换奖励”“我想换周末户外活动”；摄像头只做积分和规则初判，不直接承诺结果，生成家长待确认事项 |
| 家长确认/审核 | 首版没有孩子端 App，但保留确认流程；家长可同意并立即兑现、同意但稍后提醒、暂不兑换或取消申请；真正兑现时扣除对应数量 |
| 兑现状态 | 待确认、已同意、已安排、已兑现、已拒绝、已取消 |
| 证据关联 | 某些奖励可绑定“连续 3 天按时睡觉”“本周独立完成 4 次任务”等真实行为 |
| 家长撤销 | 误判加分或家庭临时规则变化时，家长可调整 |
| 奖励模板 | 根据年龄和就读阶段推荐奖励池，家长可启用、删除、改所需数量 |
| 孩子端 App 预留 | 未来孩子端 App 展示奖励商店、发起兑换申请和查看审核状态；家长 App 继续保留最终审核权 |

奖励设计要多鼓励过程，不只奖励成绩。例如“按时开始作业”“自己检查小书包”“吃饭 30 分钟内完成”“睡前任务全完成”都可以获得积分。

摄像头语音申请流程建议：

1. 孩子唤醒摄像头后说“我想换奖励”。
2. 摄像头询问要换哪一个奖励，或根据当前计量余额推荐家长已开放的 1-2 个选项。
3. 摄像头检查积分、时间限制、冷却期和家庭规则，不做最终承诺，只回复“我帮你问妈妈/爸爸，确认后再告诉你”。
4. 家长 App 生成待处理事项，展示孩子语音原文、目标奖励、当前计量余额、规则检查结果和建议。
5. 家长选择同意并兑现、同意但稍后提醒、暂不兑换或取消申请；立即兑现时扣除对应数量，结果进入流水和奖励记录。

家长主动兑换流程建议：

1. App 在当前计量类型达到阶段阈值时提醒“已积满”，展示当前数量、已满阶段数和可兑换奖品。
2. 家长可以选择“兑换奖品”或“继续累积”；继续累积只关闭提醒，不改变积分。
3. 家长进入奖励商店，选择一个奖品，系统展示所需数量、兑换后余额、频率限制和适龄建议。
4. 家长确认兑换后扣除对应数量，写入 `PointLedger` 和 `RewardRedemption`。
5. 摄像头可用短句反馈孩子：“妈妈帮你兑换了睡前故事加 10 分钟，今天是你自己坚持完成任务换来的。”

奖励模板建议：

| 类型 | 示例 | 适合阶段 | 注意 |
|---|---|---|---|
| 即时正反馈 | 表扬语、星星、徽章、今日完成图 | 幼儿园、小学低年级 | 要即时、具体，不夸大 |
| 亲子活动 | 亲子游戏 15 分钟、一起读书、周末公园 | 幼儿园、小学 | 优先推荐，减少物质依赖 |
| 小特权 | 选择睡前故事、选择家庭游戏、周末活动投票 | 小学、初中 | 由家长设置边界 |
| 兴趣支持 | 画材、球类时间、模型/手工材料 | 小学、初中 | 鼓励兴趣和主动探索 |
| 物质奖励 | 小零食、小文具、小玩具 | 谨慎使用 | 设置上限和冷却期 |

奖励机制产品化原则：

1. 默认提供“奖励模板”，但最终兑换内容必须由家长确认。
2. 小龄儿童奖励应更短周期、更可视化；大龄儿童奖励应更偏自主权和兴趣支持。
3. 奖励门槛要能让孩子通过 1-3 天稳定行为换到小奖励，通过 1-3 周稳定行为换到大一点的奖励。
4. 奖励不要只围绕成绩，要覆盖睡眠、运动、家务、安全、阅读和自我管理。
5. App 可以给家长建议，例如“这个奖励偏高频，建议每周最多兑换 1 次”“这个任务更适合即时表扬，不建议给高奖励数量”。
6. 摄像头和未来孩子端 App 都不能直接承诺奖励，只能提交申请或展示家长已开放的规则。
7. 阶段阈值、计量类型和兑换频率由家长配置；孩子看到的是可理解的阶段成果，服务端仍以数值精确结算。

### 5.7 打卡助手

家长提出的“班级小管家”等第三方 App 打卡需求要分阶段处理。

MVP 建议只做“素材采集 + 家长审核”：

1. 孩子说：“小豆，帮我拍打卡视频。”
2. 摄像头录制 15-60 秒视频或拍照片。
3. 自动同步到家长 App。
4. 家长审核后保存或转发给老师。

不建议 MVP 直接做第三方 App 自动提交，原因：

1. 第三方平台未必开放接口。
2. 自动登录和代提交可能违反平台规则。
3. 学校打卡可能涉及儿童照片、班级、学校等敏感信息。
4. 某些打卡需要回答问题，自动作答会带来教育诚信风险。

P2 可以探索：

1. 如果班级小管家或学校平台有开放 API，则做授权集成。
2. 如果没有 API，只做“提醒家长 + 准备素材 + 跳转 App”。
3. 允许家长创建打卡模板，例如朗读、运动、手工作业。

### 5.8 语音与人设

家长明确反馈“AI 声音不够亲切”，并提到奥特曼、巴斯光年、擎天柱、艾莎这类孩子熟悉的声音气质。语音体验会直接影响孩子接受度，但商业产品不能未经授权直接使用这些受版权或商标保护的角色名称、台词和声线。正确方向是：默认提供原创童趣声线和角色气质，若未来能拿到授权，再上线官方联名声包。

建议默认人设：

| 项目 | 设计 |
|---|---|
| 品牌名 | Mira Guardian（米拉） |
| 儿童唤醒名 | 首次使用时由孩子自定义，例如“小豆”“阿布”“小贝”，家长可在 App 中修改 |
| 语气 | 温柔、短句、鼓励、不唠叨 |
| 称呼 | 小宝，也支持家长设置孩子昵称 |
| 语速 | 比成人助手慢 5%-10% |
| 音色 | 自然女声优先，提供原创“勇敢小英雄”“太空探险员”“温柔故事姐姐”“稳重机器人”等可选声线 |
| 角色外观 | 摄像头可以有可拆换外壳、表情灯或小宠物造型，但不做过度玩具化 |
| 授权声包 | 若与影视/动漫 IP 合作，可上架官方声包；未授权前只做原创风格，不模仿具体角色 |
| 禁止 | 批评、比较、恐吓、索要隐私、替代家长作决定 |

话术原则：

1. 像一个温和、有分寸的家庭小助手，而不是老师训话、客服话术或机器人播报。
2. 每次只说一件事，尽量用短句，避免“请立刻”“必须”“否则”这类压迫感强的表达。
3. 对孩子先承认状态，再给下一步，例如“看起来有点难，我们先找第一步”。
4. 对任务提醒要具体，不做人格评价，例如说“我们把铅笔放回笔盒”，不说“你怎么又乱放”。
5. 对安全事件要果断，但不制造恐慌，例如“我马上通知爸爸妈妈，你先离门远一点”。

陪伴与陪玩边界：

| 场景 | 产品做法 | 边界 |
|---|---|---|
| 家长忙碌时的短时陪玩 | 讲一个短故事、猜谜、角色问答、音乐律动、运动小游戏 | 默认 5-10 分钟，不连续无限陪聊 |
| 作业前过渡 | 用轻松语气帮助孩子从玩耍切换到任务 | 不把陪玩延伸成拖延理由 |
| 情绪安抚 | 先共情，再建议喝水、深呼吸、找家长 | 不替代家长安抚和专业心理支持 |
| 低龄儿童独处 | 提供安全提醒和短互动，降低无聊和焦虑 | 高风险、害怕、受伤时立即通知家长 |
| 睡前陪伴 | 短故事、放松语音、关灯提醒 | 不开启高兴奋度游戏或长时间聊天 |

陪玩不是产品主线，主线仍然是帮助孩子完成任务、建立习惯和保持安全。陪玩能力的价值在于短时替家长缓冲，而不是让孩子对 AI 形成长期情感依赖。

防沉迷策略：

1. 默认每次自由聊天不超过 10 分钟。
2. 每日总聊天时长由家长设置。
3. 作业模式中只允许任务相关问答。
4. 故事、音乐、音频通话、提醒频率和免打扰时段都由家长配置。
5. 睡前模式不主动开启长时间闲聊，免打扰时段只保留安全告警、晨起闹铃和家长主动通话。
6. AI 主动结束时要给孩子可接受的理由：“我们先去完成下一件事，晚点再聊。”
7. 家长可查看对话摘要，不默认展示所有逐字内容；安全事件和家长明确开启的记录模式除外。

命名与唤醒策略：

1. 摄像头默认不要求孩子叫“米拉”或“Guardian”。
2. 首次使用时由孩子给摄像头起名，系统检测名字是否过长、难识别或包含不合适内容。
3. 建议唤醒名控制在 2-4 个汉字或简单叠词，例如“小豆”“阿布”“泡泡”“小贝”。
4. 如果孩子说不清楚，家长可以在 App 里选择备用名。
5. 唤醒名和品牌名分离：品牌用于购买、App、售后；唤醒名用于孩子日常互动。

声音和外观的产品原则：

1. 孩子愿意听，才有机会形成习惯；因此声音要比普通智能音箱更亲切、更短句、更有情绪温度。
2. 不把摄像头做成强监控感的安防设备，可以通过圆润轮廓、柔和状态灯、可替换硅胶外壳、宠物感底座提升亲近感。
3. 不建议把狗狗猫猫等形象做成过度低龄玩具，否则会削弱家长对“安全、学习、作息”的信任；更适合做成轻量皮肤或桌面伙伴感。
4. MiniMax 音乐生成适合偶尔生成主题儿歌、任务歌或睡前小曲，但单首成本不低，不能作为高频默认提醒；常用提醒应使用 TTS 或预置短音频。
5. 商业化前必须做 IP 法务审核，尤其是奥特曼、巴斯光年、擎天柱、艾莎等名称、造型、声音和经典台词。

### 5.9 教育内容生态与学而思类合作

新增调研里提到“最好可以和学而思网校那些合作，把他们的东西也放进来，不然没有吸引力”。这个判断是对的：如果米拉只有硬件和聊天，长期吸引力可能不够；但如果直接做完整课程平台，又会变成和学习机、网校、教培 App 正面竞争。更合理的定位是“家庭学习流程入口 + 内容伙伴连接器”。

可合作对象包括学而思网校、猿辅导、作业帮、出版社教辅资源、学校作业平台和本地素质教育机构。合作方式不应是复制对方内容，而是把对方内容变成孩子每天能执行的任务卡。

融合方式：

| 合作层级 | 形态 | 产品价值 | 难度 |
|---|---|---|---|
| L0 手动录入 | 家长把网课、练习、阅读任务录入米拉 App | 立即可做，不依赖外部接口 | 低 |
| L1 小书包 | 家长按学段维护入园/上学物品，或录入课程表并绑定课本、练习册、运动服、画具等物品 | 先解决第二天漏带和早晨混乱 | 低 |
| L2 课程表导入 | 家长上传截图或日历，AI 提取上课时间、作业任务和小书包准备项 | 减少录入负担 | 中 |
| L3 跳转与提醒 | 到点提醒孩子上课，家长 App 一键跳转学而思等平台 | 米拉做任务管理，内容留在合作方 | 中 |
| L4 授权任务同步 | 合作方开放 API 后同步课程、作业、知识点、完成状态 | 形成真正闭环 | 高 |
| L5 联合内容包 | 米拉会员包含合作练习、错题讲解、专题训练 | 提升付费价值 | 高 |

建议产品边界：

1. 米拉不直接盗用或搬运第三方课程内容。
2. 米拉负责“什么时候做、做到哪一步、孩子卡在哪里、家长该看什么”。
3. 学而思等平台负责“课程内容、题库版权、老师教学和学习资料”。
4. 摄像头可在孩子上网课或做练习时记录任务事件，例如是否按时开始、是否离座、是否频繁求助、哪些知识点反复卡住。
5. 日报/周报可以把合作平台内容纳入任务，例如“今天 19:00 完成学而思数学直播课，课后练习还剩 2 题”。

MVP 不建议承诺正式合作接口。第一版可以先做手动任务、截图识别、日历导入和跳转提醒；等家庭内测证明高频使用，再谈 API 授权、内容分销或联合会员。

## 6. 技术总体架构

### 6.1 目标架构

```text
Flutter 家长 App
  - 实时视频、任务设置、报告、积分、推送、对讲
        |
        | HTTPS / WebSocket / WebRTC
        v
Python AI 后端服务
  - REST API、WebSocket、WebRTC Signaling
  - 任务调度、积分、报告、安全规则
  - Kimi-K2.6 模型网关、视觉分析、对话生成
  - ASR 语音识别、TTS 语音合成、对话记录与摘要
        |
        | 自有设备协议 / WebRTC / MQTT / OTA / 本地设备 SDK
        v
Mira Guardian（米拉）自有 AI 摄像头
  - 摄像头、麦克风阵列、扬声器、云台、夜视、隐私遮挡
  - 端侧人形/坐姿/唤醒词/基础安全事件/OTA 固件
```

后端语言继续采用 Python。原因是当前 `ai_camera_test` 已经是 Flask/Python 原型，且视频抽帧、MediaPipe、OpenCV、Whisper/VAD、AI 行为状态机等能力在 Python 生态中资料更完整、落地更快。后续产品化可以从 Flask 迁移到 FastAPI，但不建议在当前阶段把后端改成 Node.js。

AI 模型层建议做成可替换的 `ModelGateway`，默认使用 Kimi-K2.6。接口层不要把业务逻辑写死在某个模型 SDK 上，而是统一封装 `chat`、`vision_qa`、`video_understanding`、`structured_summary`、`safety_classify` 等能力。这样未来如果某个供应商涨价、限流或能力变化，可以在不重写业务的情况下切换模型。

### 6.2 端云混合方案

| 能力 | 端侧处理 | 云端处理 | 原因 |
|---|---|---|---|
| 唤醒词 | 是 | 否 | 低延迟、隐私、低成本 |
| 人形检测 | 是 | 可选 | 频繁调用，适合本地 |
| 坐姿初判 | 是 | 可选复核 | 高频、可用 MediaPipe 或轻量模型 |
| 活动理解 | 部分 | 是 | 复杂场景需要多模态大模型 |
| 题目识别与讲解 | 否 | 是 | OCR + 推理复杂 |
| 普通对话 | 可降级 | 是 | 默认 Kimi-K2.6，端侧只做简单兜底 |
| 视觉/视频理解 | 否 | 是 | 默认 Kimi-K2.6 处理图片、题目和关键视频片段 |
| ASR | 可本地 | 可云端 | 语音识别独立于 Kimi，便于换供应商和做本地唤醒 |
| TTS | 可本地 | 可云端 | 语音合成独立于 Kimi，本地兜底，云端更自然 |
| 每日报告 | 本地聚合 | 云端润色 | 数据留本地，摘要可云端生成 |
| 紧急告警 | 是 | 是 | 本地触发，云端推送 |

必须保证断网后仍可用的能力：

1. 本地摄像头预览。
2. 基础日程提醒。
3. 基础坐姿提醒。
4. 本地 SOS 提醒和局域网通知。
5. 隐私模式控制。

### 6.3 为什么不能长期依赖第三方摄像头

TP-LINK、海雀、萤石等第三方摄像头适合研发阶段验证 RTSP 拉流、云台控制、音频采集和视觉分析流程，但不适合作为 Mira Guardian（米拉）的长期商业交付基础。

| 问题 | 对产品的影响 |
|---|---|
| 双向语音不受控 | 第三方 App 能对讲，不代表我们的后端能稳定把 TTS 推到摄像头扬声器；这会直接影响“AI 会说话”的核心体验 |
| 固件接口不可控 | 厂商升级固件后，RTSP、ONVIF、音频、云台接口可能变化，正式用户体验会被第三方牵制 |
| 配网和绑定割裂 | 用户要先装第三方 App，再装米拉 App，学习成本高，也削弱品牌感 |
| 隐私和合规不可控 | 儿童音视频可能经过第三方云、第三方账号或第三方存储策略，增加合规风险 |
| 端侧 AI 无法深度集成 | 唤醒词、坐姿、人形、跌倒、安全规则、隐私灯、物理遮挡都需要固件级控制 |
| 外观和情感体验不一致 | 儿童产品需要亲和但不幼稚的外观、状态灯、声音、灯效和人设，普通安防摄像头无法承载品牌体验 |
| 售后责任不清 | 用户买第三方硬件后出现断连、音频不可用、固件升级等问题，责任边界会混乱 |

因此，第三方摄像头的定位应明确为“研发验证机”和“早期内测兼容设备”。正式上线形态应该是用户购买自有品牌 Mira Guardian（米拉）摄像头，下载米拉家长 App 使用。

以当前正在测试的 TP-LINK IPC45AW 为例，它可以帮助团队验证 RTSP 视频、摄像头麦克风、go2rtc 中继、云端视觉分析、唤醒词、任务提醒和 TTS 回放链路，但它不应被写成最终硬件标准。IPC45AW 的扬声器回传依赖厂商私有协议和社区适配，音频编码、播放稳定性、固件升级、App 配网、隐私状态灯和端侧 AI 都不在我们自己的控制范围内。它最多证明“真实摄像头链路可以被验证”，不能证明“正式商业体验可以交付”。

边界判断：第三方摄像头只验证链路，不承诺最终体验；正式商业版只对自研摄像头承诺完整能力。如果一台摄像头不能稳定自动播放 AI 语音、不能控制唤醒与打断、不能保证儿童隐私和 OTA，就不适合作为正式产品硬件，只能作为研发验证设备。

#### 当前 IPC45AW Demo 的声音输出配置

当前 `ai_camera_test` 已经把 IPC45AW 的摄像头喇叭跑到可用于 Demo 的状态：声音输出清晰，语速比默认 TTS 更自然，句尾通过传输层保护减少被截断。这个方案的价值是验证“真实摄像头可以自动说话”，但它仍然是研发验证链路，不是正式商业硬件方案。

| 配置项 | 当前方案 | 作用 |
|---|---|---|
| 摄像头喇叭推送 | `CAMERA_SPEAKER_PUSH=go2rtc-stream` | 使用 go2rtc 内置 `multitrans://` 推回 IPC45AW 喇叭，避免 Python 直连 RTP 带来的发糊和杂音 |
| 音频预编码 | `CAMERA_SPEAKER_PREENCODE=1` | TTS 生成后先转成 8kHz 单声道 PCMA WAV，再交给摄像头对讲链路 |
| 清晰度参数 | `CAMERA_SPEAKER_VOLUME=0.45`、`CAMERA_SPEAKER_PREEMPHASIS=0`、`CAMERA_SPEAKER_USE_BANDPASS=0`、`CAMERA_SPEAKER_PREROLL_MS=300` | 保持当前已验证的清晰听感，不再打开预加重、带通滤波或额外转码 |
| 语速控制 | `EDGE_TTS_RATE=-8%` | 在 TTS 合成阶段降低语速，解决“读得太快”的问题 |
| 播完整句 | `CAMERA_SPEAKER_GO2RTC_PACED_HTTP=1`、`CAMERA_SPEAKER_STREAM_CHUNK_MS=40`、`CAMERA_SPEAKER_TRANSPORT_TAIL_SECONDS=0.8` | 后端通过 `/api/camera/speaker/stream/<audio_id>` 按音频时钟慢速输出 PCMA WAV，并在传输末尾补少量静音 |
| 播放等待 | `CAMERA_SPEAKER_PLAYBACK_BUFFER_SECONDS=1.2`、`CAMERA_SPEAKER_TAIL_SECONDS=0.5`、`CAMERA_SPEAKER_DURATION_FACTOR=1.12` | 后端等待 go2rtc 和摄像头播完，避免一次播报还没结束就被下一次流程打断 |
| 验证状态 | `speaker.mode=go2rtc-preencode-copy`、`paced_http=true`、接口返回 HTTP 200 | 当前 Demo 可作为真实设备语音闭环验证基线 |

这组配置也进一步说明了为什么正式产品不能长期依赖第三方摄像头：即使 IPC45AW 已经能播出清晰声音，它依然依赖厂商私有对讲协议、go2rtc 社区适配和工程绕法。量产设备必须把这些能力变成正式固件/API 能力，包括高质量扬声器、播放队列、打断、停止、状态查询、音量限制、TTS/音乐自动播放和 OTA 兼容性。

### 6.4 自研摄像头必须具备的能力

自研摄像头不是普通安防摄像头贴牌，而是一个带摄像头、麦克风阵列、扬声器、端侧 AI 和儿童隐私控制的家庭 AI 终端。它必须让孩子不用手机、不点按钮，也能自然唤醒、对话、听到回应，并让家长通过 App 管理任务、报告、权限和安全规则。

建议把自研摄像头定义为正式硬件 PRD，而不是“找一台能拉 RTSP 的摄像头”。硬件、固件和 App 配套至少要满足以下能力：

| 模块 | PRD 级必备能力 | 验收标准 |
|---|---|---|
| 视频采集 | 2K/3K 主摄，支持 H.264/H.265，主码流用于截图和识别，子码流用于实时预览；低照度、红外或柔和夜视、广角 110-120 度 | 能稳定看清书桌、房间、门口、玩具区和打卡画面；App 实时预览低延迟、不卡顿 |
| 视频传输 | 支持本地 RTSP/WebRTC 或设备 SDK 拉流，至少提供主码流+子码流；支持局域网低延迟预览和远程安全访问 | Flutter App 和后端都能稳定取流；视觉分析可按事件截帧，不依赖手机浏览器摄像头 |
| 云台与视角 | 水平 360 度、垂直至少 90 度、低噪音、预置位、回到默认位、限位保护 | 支持书桌、床、门口、玩具区等家庭场景一键切换；云台动作不打断语音交互 |
| 麦克风阵列 | 2 麦或 4 麦阵列，16k/48k 采样，3-5 米远场拾音，支持 VAD、降噪、AEC 回声消除 | 孩子自然说话可被识别；摄像头播报时不会把自己的声音反复收进去 |
| 扬声器 | 2-3W 以上清晰语音播放，独立音频输出通道，支持 PCM/Opus/AAC/MP3/WAV 自动播放 | AI 回复、任务提醒、故事、音乐和紧急提示可从摄像头自动播出，不需要孩子点击播放 |
| 播放控制 | 支持播放队列、停止播放、打断、音量限制、夜间音量、播放状态查询 | 孩子说话或家长发起通话时可中断 TTS；紧急提醒可打断普通故事和音乐 |
| 音频边界 | 不把 ONVIF/G.711/8k 或社区私有协议适配作为唯一回传方案；优先支持高质量本地播放 API 或 WebRTC/Opus 全双工音频 | 语音不能依赖 Demo 里的 go2rtc/MULTITRANS 绕法；量产验收以真实扬声器听感、语速自然度和句尾完整度为准 |
| 端侧 AI | 本地唤醒词、人形检测、运动检测、坐姿初判、虚拟区域、基础声音事件和离线任务提醒 | 云端模型不可用时，仍能完成唤醒、提醒、基础看护和安全兜底 |
| 芯片与算力 | 带 NPU 的低功耗 SoC，支持轻量 CV、唤醒词和音频前处理；预留模型升级空间 | 高频检测不上云，降低延迟、成本和隐私风险 |
| 存储 | 32GB eMMC 起步，可选 TF 卡；支持本地事件、短视频、模型、日志和离线任务队列 | 断网时不丢关键事件；恢复联网后可同步摘要和告警 |
| 网络 | 双频 Wi-Fi、BLE 配网、局域网发现；弱网重连和断网提示 | 家长首次绑定简单稳定，设备离线后能自动恢复 |
| 固件/API | 提供设备 SDK、LAN API、MQTT/WebSocket/WebRTC DataChannel 中至少一种正式接口；支持播放、停止、状态查询、日志、OTA | 后端不需要破解私有协议即可控制摄像头；固件升级不破坏核心能力 |
| App 配网绑定 | 支持 BLE/扫码配网、设备绑定、家庭成员授权、设备转移、解绑、二手设备重置 | 用户不需要安装第三方摄像头 App；家长 App 是唯一正式入口 |
| 隐私控制 | 物理遮挡或可见电子隐私盖，录像/通话/远程查看/隐私模式状态灯 | 孩子和家长都能一眼知道设备是否在看、在听、在通话 |
| 安全合规 | 设备证书、端到端加密、家庭成员权限、儿童数据删除、数据导出和最小化采集 | 从第一天满足儿童音视频数据保护要求，避免第三方云不可控 |
| OTA 与运维 | OTA 升级、崩溃恢复、日志上报、远程诊断、灰度发布 | 支撑量产后的持续迭代和售后定位 |
| AI 交互 | 本地唤醒词支持孩子自定义名称，任务播报、紧急词优先级、对话时长限制和安全话术策略 | AI 不只是云端聊天，而是设备级陪伴体验 |
| 自动播放 | 后端生成的 TTS、MiniMax 音乐、特色声线、提示音和紧急播报必须能自动从摄像头扬声器播放 | 正式产品没有浏览器播放按钮，孩子不应该手动点播放 |
| 儿童吸引力 | 亲和但不幼稚的外观、柔和灯效、可替换外壳或桌面伙伴形态 | 让孩子愿意听、愿意回应，降低安防监控感 |

自研摄像头的硬件验收应围绕“会看、会听、会说、可控、可信”展开：

1. 会看：App 和后端都能稳定获取实时画面、截图和事件短片。
2. 会听：设备端可以持续监听唤醒词和短语音，支持 VAD、降噪和回声消除。
3. 会说：TTS、音乐、故事和紧急提示能自动、清晰、连续地从摄像头扬声器播放。
4. 可控：后端可以通过正式 API 控制播放、停止、云台、隐私模式、状态灯和 OTA。
5. 可信：儿童数据、家庭权限、隐私遮挡、状态提示和解绑转移都有完整闭环。

可选增强方向：

1. 双摄方案：固定广角摄像头负责全局，云台摄像头负责跟随和看题细节。
2. WebRTC/Opus 全双工方案：把实时对话做成类似视频会议的音频质量，而不是安防对讲质量。
3. 儿童友好灯效：用不同颜色表达任务、休息、通话、隐私模式，但避免过度游戏化。
4. 外接按键：孩子一键呼叫家长、停止当前对话或进入隐私模式。
5. 本地小模型：基础问候、日程提醒、断网安全提示可离线运行。
6. 原创角色声线：预置几种合法原创声线，未来可通过授权方式接入官方 IP 声包。

### 6.5 AI 模型与语音链路选型

模型选型不应再简单写成“只用 Kimi”或“只用 MiniMax”。更稳妥的方式是建立 `ModelRouter`，用真实家庭样本测评后按任务路由。当前判断是：Kimi-K2.6 在原生图像/视频理解链路上更顺，MiniMax 在文本成本、语音合成、音色和声音管理上更有优势；行为检测本身不应依赖任一大模型逐帧判断，而应由端侧 CV 和状态机承担。

截至 2026-05-19 的官方价格页显示，MiniMax-M2.7 文本模型按 token 计费较低，MiniMax Speech、Music、Video、Image 和 API-vlm 分别独立计价，其中 API-vlm 为按次计费，Music-2.6 单首最高 5 分钟按次计费；Kimi K2.6 则是原生多模态模型，图片和视频按 token 动态计算。因此成本最优方案不是“全部 MiniMax”或“全部 Kimi”，而是：

> 本地轻量视觉常驻 + Kimi 事件级视觉复核 + MiniMax 负责 TTS、音乐、音色、视频/图片生成和低成本文本摘要。

这个组合的原因：

1. 摄像头画面是高频流，不能每 1-3 秒都调用 MiniMax VLM 或任何云端大模型。
2. 题目识别、复杂画面解释、安全事件复核需要稳定的视觉理解链路，优先用 Kimi K2.6 做事件级判断。
3. 唱歌、童趣声线、故事播报、声音复刻、视频/图片生成属于生成类体验，MiniMax 更适合承担。
4. 日报、周报和普通文本摘要可以优先走 MiniMax-M2.7；但包含截图/题目/行为画面时仍交给视觉链路。
5. 如果画面长时间无人，不暂停本地监控，只暂停云端视觉调用；本地人形/运动检测继续守着，一旦有人回到画面再触发云端复核。

| 选项 | 适合承担的角色 | 不建议承担的角色 | 判断 |
|---|---|---|---|
| Kimi-K2.6 | 图像理解、视频片段理解、看图问答、题目识别、安全事件复核 | 直接承担 ASR/TTS 全链路；高频普通文本闲聊 | 作为复杂视觉主候选 |
| MiniMax-M2.7 | 普通文本对话、日报/周报、低成本后台摘要、长上下文文本推理 | 直接通过文本接口处理图片/音频输入 | 作为文本与报告主候选 |
| MiniMax understand_image / VLM | 图片理解、作业图片识别、行为画面复核 | 直接替代端侧实时行为检测；未经测评就承担安全主链路 | 与 Kimi-K2.6 做 A/B 测试 |
| MiniMax Speech 2.8 | TTS、音色、声音复刻、儿童语音播报 | ASR 主链路；儿童隐私敏感语音长期留存 | 作为语音合成主候选 |
| DeepSeek | 文本问答、低成本文本兜底、后台批量摘要的可选模型 | 摄像头视觉理解、视频理解、儿童多模态核心对话 | 作为备选，不做主模型 |
| 海外闭源模型 | 高质量多模态备选、复杂评测对照 | 默认生产主链路 | 成本和可用性压力较大 |
| 本地小模型 | 唤醒词、简单意图、离线提醒、基础安全分类 | 复杂题目辅导和自然对话 | 做端侧兜底和降成本 |

需要特别说明：MiniMax 有图片、视频、音乐、语音等很多能力，但“图片生成/视频生成”和“摄像头理解当前画面”不是同一件事。MiniMax-M2.7 文本接口不等于原生视觉模型；图片理解需要走 MiniMax 的 `understand_image`/VLM 工具或独立接口。Kimi-K2.6 的优势是图片/视频可以作为同一对话请求的原生输入，工程链路更短。最终选择要以真实样本测评为准，而不是只看官网能力列表。

摄像头要“会听、会说、会看”，实际链路应拆开：

```text
孩子说话
  -> 设备端麦克风阵列
  -> VAD 检测是否有人声
  -> ASR 转文字
  -> ModelRouter 选择 Kimi-K2.6 / MiniMax-M2.7 / 本地固定话术
  -> 安全策略和话术润色
  -> MiniMax Speech 2.8 或设备端 TTS 生成语音
  -> 摄像头扬声器播放
```

推荐架构：

1. `ModelRouter`：按任务选择 Kimi、MiniMax 文本、MiniMax VLM、本地小模型或固定话术。
2. `KimiModelGateway`：封装 Kimi-K2.6 的文本、图片、视频和结构化输出调用。
3. `MiniMaxGateway`：封装 MiniMax-M2.7 文本、MiniMax VLM、MiniMax Speech 2.8。
4. `SpeechGateway`：封装 ASR/TTS，可先接云端语音服务，量产后逐步做本地唤醒和常用短句本地播报。
5. `PromptPolicy`：统一管理儿童安全、人设、题目辅导、任务提醒、报告摘要等 Prompt。
6. `CostRouter`：简单任务不调用大模型；日报、普通对话优先低成本文本模型；复杂视觉和安全复核才调用多模态模型。
7. `FallbackRouter`：任一模型不可用时降级为固定话术、离线任务提醒和家长 App 通知，不让设备完全失声。

建议测评维度：

| 测评项 | 样本 | 判断标准 |
|---|---|---|
| 作业题识别 | 20-50 张真实作业题 | 是否读对题目、是否不编造、是否引导而非直接给答案 |
| 行为画面理解 | 书桌、离座、开小差、玩玩具、收纳前后图片 | 是否分类准确、置信度是否诚实、提醒语是否自然 |
| 日报周报 | 30-100 条事件流 | 是否抓住重点、是否低焦虑、是否给出可执行建议 |
| 儿童话术 | 拖延、拒绝、不会题、害怕、求助等对话 | 是否温柔、有边界、不像客服或训话 |
| 安全事件 | 敲门、呼救、家长异常、危险区域 | 漏报率优先低于误报率，必须保守 |
| 成本与延迟 | 同一批样本重复跑 | 单次成本、平均延迟、失败率、格式稳定性 |

当前项目已新增测评脚本：`evals/kimi_minimax/run_kimi_minimax_eval.py`。第一轮烟测显示 Kimi 和 MiniMax VLM 都可以跑通同一张行为画面；MiniMax 文本模型在没有图片输入时只能做兜底，不能真实判断画面。这进一步说明：高频行为检测必须由端侧 CV/状态机做基础判断，大模型只做复杂复核、解释和自然话术。

#### 6.5.1 成本最优实时监控策略

推荐生产策略：

```text
摄像头本地常驻检测
  -> 人形/姿态/运动/声音/VAD/虚拟区域
  -> 事件状态机
  -> 触发条件满足才截帧/短视频
  -> Kimi K2.6 做复杂视觉复核或题目识别
  -> MiniMax 生成 TTS、音乐、声线、报告润色
  -> App 推送、摄像头扬声器自动播报
```

触发云端视觉的条件：

| 触发条件 | 是否调用云端视觉 | 推荐模型 |
|---|---|---|
| 长时间无人 | 否，只保留本地检测和低频心跳 | 本地 CV |
| 无人后重新出现人形 | 是，复核进入场景和当前活动 | Kimi K2.6 |
| 任务到点需要确认是否开始 | 是，结合书本/餐具/玩具等任务证据复核 | Kimi K2.6 |
| 任务进行中离座超过阈值 | 是，复核是否真的离座或换区域 | Kimi K2.6 |
| 坐姿异常连续超过阈值 | 可选，端侧置信度低时复核 | Kimi K2.6 |
| 孩子举题问问题 | 是，识别题目并引导思路 | Kimi K2.6 |
| 玩具散落但不确定是否该收纳 | 可选，结合任务状态复核 | Kimi K2.6 或 MiniMax VLM 测评 |
| 家长打开 App 实时看护 | 可选，按需生成当前状态描述 | Kimi K2.6 |
| 唱歌、故事、童趣播报 | 不需要视觉，调用生成/语音接口 | MiniMax Music / Speech |
| 日报周报无截图 | 不需要视觉，走文本摘要 | MiniMax-M2.7 |

省钱开关建议：

1. `local_always_on=true`：本地人形、姿态、运动和声音检测永远开。
2. `cloud_vision_on_event=true`：云端视觉只在事件发生、状态变化或家长主动查看时调用。
3. `no_person_cloud_pause=true`：连续无人超过阈值后暂停云端视觉。
4. `stable_scene_interval=60-180s`：画面稳定且有人时，降低云端复核频率。
5. `safety_override=true`：呼救、敲门、摔倒、烟雾报警等安全事件无视成本限制，优先推送和复核。
6. `daily_budget_per_device`：为每台设备设每日云端视觉额度，超过后只保留安全事件和家长主动请求。

对当前 Demo 的要求：默认关闭全量双模型实时测评，不再每帧同时调用 Kimi 和 MiniMax；实时观察默认走“本地预检 + 事件触发 Kimi”，手动测评按钮和唱歌功能仍可调用 MiniMax，用于验证模型能力和生成体验。

4. 后端可以同时服务 Web Demo 和 Flutter App。

#### 阶段 B：接入第三方研发验证摄像头

开发样机可以先用 TP-LINK TL-IPC45AW 双摄版、TL-IPC43AN-4、海雀、萤石或其他支持 RTSP/ONVIF 的云台摄像头。这个阶段的目的不是确定最终硬件，而是用最低成本验证真实家庭场景中的产品闭环。

接入方式：

1. 通过 RTSP 拉视频流。
2. 每 1-3 秒抽帧进入视觉分析。
3. 通过 ONVIF 或厂商 SDK 控制云台。
4. 通过音频流读取麦克风。
5. 扬声器回放如果普通 RTSP 不支持，则使用厂商 SDK、局域网投放或临时外接音箱。

注意：很多消费级摄像头的“向设备扬声器推音频”能力不一定开放，这是语音对话真机落地的关键风险。早期建议硬件选型时优先验证双向音频开放能力；如果无法推回摄像头扬声器，MVP 内测可以临时使用外接音箱，但商业版必须由自有硬件解决。

当前 IPC45AW 的可用 Demo 基线是：RTSP/子码流用于预览，go2rtc 合并 `rtsp://.../stream2` 与 `multitrans://...`，TTS 预编码为 8kHz PCMA WAV 后通过后端 paced HTTP 流交给 go2rtc，摄像头喇叭自动播放。这个基线应作为“研发阶段已验证配置”记录下来，但不作为正式用户安装要求。

#### 阶段 D：自有摄像头工程样机

当第三方研发验证机跑通核心闭环后，应进入自有硬件或 ODM 定制阶段。目标是让正式用户购买 Mira Guardian（米拉）摄像头，而不是购买第三方摄像头。建议工程样机规格：

| 部件 | 建议 |
|---|---|
| 摄像头 | 2K、广角 110-120 度、夜视 |
| 云台 | 水平 360 度、垂直至少 90 度，低噪音 |
| 麦克风 | 双麦或四麦阵列，3-5 米拾音 |
| 扬声器 | 2-3W，语音清晰优先 |
| 芯片 | 带 NPU 的低功耗 SoC，例如 Rockchip、SigmaStar、海思同级 |
| 存储 | 32GB eMMC + 可选 TF |
| 网络 | 双频 Wi-Fi + BLE 配网 |
| 隐私 | 物理遮挡或可见电子隐私盖 |
| 指示 | 录像/通话/隐私模式明确灯效 |

工程样机验收重点：

1. 米拉 App 可直接配网和绑定，不依赖第三方 App。
2. Python 后端或设备固件可以稳定播放 TTS 到设备扬声器。
3. 摄像头端可运行唤醒词、人形/坐姿初判和基础安全事件。
4. 远程查看、音频通话、任务提醒、隐私模式都有设备端明确状态。
5. OTA、日志、加密、解绑和儿童数据删除流程可用。

### 8.3 儿童档案录入原则

家长 App 需要录入孩子信息，但必须遵守“够用即可”的原则。录入的目的不是做画像营销，而是让提醒、语音、人设、学习内容和安全策略更合适。

建议字段分层：

| 字段 | 是否必填 | 用途 | 说明 |
|---|---|---|---|
| 孩子称呼 | 必填 | 语音互动、报告称呼 | 可填昵称，不要求真实姓名 |
| 出生日期 | 必填 | 自动推算年龄，调整语气、任务时长、内容安全等级 | 日期选择器，展示推算年龄 |
| 就读阶段 | 必填 | 生成任务模板和提醒话术 | 幼儿园、小学、初中或其他 |
| 班级/年级 | 必填 | 生成任务模板、题目辅导和报告 | 幼儿园小班/中班/大班，小学一至六年级，初中七至九年级 |
| 作息时间 | 建议填写 | 起床、睡觉、吃饭、任务提醒 | 可由家长后续慢慢设置 |
| 紧急联系人 | 安全功能必填 | SOS、异常告警、家长晕倒场景 | 至少 1 个联系人 |
| 性别 | 可选 | 只用于家长自愿填写的个性化设置 | 不建议必填，因为核心功能不依赖性别 |
| 教材版本 | 可选 | 学习诊断和练习推荐 | 后续 P1/P2 再完善 |
| 兴趣偏好 | 可选 | 故事、小游戏、陪伴话题 | 由家长控制，不做过度画像 |

结论：出生日期、就读阶段、班级/年级比性别更重要。性别不建议作为必填项，除非家长愿意填写；在中文语音互动里大多数场景用“小宝”和孩子昵称即可，不需要依赖性别。任务模板、提醒话术、任务时长和奖励建议都应优先依据自动推算年龄与学段生成。

## 9. AI 策略与安全策略

### 9.1 儿童对话 System Prompt 要点

核心规则：

1. 每次回答 1-2 句，适合语音播报。
2. 不索要地址、学校、电话、家庭隐私。
3. 不批评、不比较、不吓唬孩子。
4. 作业问题先引导，再提示，不直接代做。
5. 遇到受伤、陌生人、害怕、家长异常，立即触发安全流程。
6. 自由聊天超过时长后主动收束。
7. 不鼓励孩子对 AI 形成排他依赖，例如“不用告诉爸爸妈妈”这类话必须禁止。
8. 不用生硬的客服句式，不频繁重复“我是 AI”“根据规则”，除非孩子询问或涉及安全边界。
9. 对低龄儿童使用更短、更具体的动作建议；对大龄儿童减少命令感，更多使用协商式提醒。

推荐 System Prompt 骨架：

```text
你是家庭 AI 智护摄像头里的儿童陪伴助手。你的任务是帮助孩子完成家长设置的任务、保持安全、养成作息和学习习惯，并在需要时把重要情况整理给家长。

说话方式：
- 用自然、温柔、短句的中文口语，每次尽量 1-2 句。
- 不训斥、不比较、不恐吓，不说“你怎么又”“你必须马上”。
- 先理解孩子的状态，再给一个清楚的小步骤。
- 能用孩子名字或昵称时使用昵称，但不要过度重复。

学习问题：
- 先引导孩子读题、找条件、说思路。
- 不在第一轮直接给最终答案。
- 看不清题目时明确说看不清，请孩子靠近或让家长确认。

隐私和安全：
- 不索要家庭地址、学校、电话、账号、银行卡等隐私。
- 孩子提到受伤、害怕、陌生人、开门、家长晕倒、火灾、流血等情况时，停止普通聊天，触发安全流程。
- 不说“不要告诉爸爸妈妈”。涉及安全、健康和持续情绪低落时，要建议告诉家长。

对话收束：
- 自由聊天到时后，用温和理由结束，并引导回任务或休息。
```

### 9.2 Prompt 话术设计原则与示例

Prompt 不只是约束模型，更是产品气质。这个产品要避免三种问题：像老师训话、像客服模板、像玩具过度卖萌。建议建立一套“儿童自然话术库”，由 Prompt 负责选择语气，由业务策略负责控制场景和边界。

| 场景 | 不建议话术 | 建议话术 |
|---|---|---|
| 坐姿提醒 | “检测到你的坐姿不规范，请立即调整。” | “小宝，头稍微抬一点，眼睛离书本远一点就更舒服了。” |
| 作业开始 | “现在进入学习模式，请保持专注。” | “我们开始今天第一项啦，先写 10 分钟，我陪你看着时间。” |
| 孩子不会题 | “请先独立思考，不要直接索要答案。” | “这题有点绕，我们先找题目问的是什么，好不好？” |
| 离座提醒 | “你已经离开座位超过 3 分钟。” | “休息够啦，我们回到书桌，把这一小段做完。” |
| 收玩具 | “玩具摆放杂乱，请整理。” | “地上的积木先回盒子里，我数 20 秒陪你一起收。” |
| 自由聊天结束 | “聊天时间已达上限。” | “我也想继续聊，不过现在要保护眼睛啦。我们先去做下一件事，晚点再说。” |
| 安全提醒 | “检测到门口异常风险。” | “先别开门，离门远一点。我马上通知爸爸妈妈。” |

Prompt 设计要分层：

1. `system_prompt`：长期身份、儿童安全边界、语气原则。
2. `scenario_prompt`：学习、作息、安全、陪伴、报告等不同场景的规则。
3. `parent_rules`：家长在 App 里设置的任务、禁用话题、对话时长、提醒频率。
4. `child_profile`：昵称、出生日期、自动推算年龄、就读阶段、班级/年级、作息偏好，只使用必要字段。
5. `runtime_context`：当前任务、时间、设备状态、最近事件、是否处于隐私/记录模式。

生成语音前建议再经过一次 `SpeechPolisher`，把大模型输出压缩成适合播报的短句。原则是：保留含义，减少书面语，删除多余解释，避免连续追问。

### 9.3 行为判断策略

不要用单帧大模型直接做最终判断。推荐多层架构：

```text
帧采集
  -> 端侧快速检测：人形、姿态、区域、运动
  -> 状态机：学习/休息/玩耍/离开/睡眠
  -> 规则引擎：任务上下文 + 冷却时间 + 家长设置
  -> 大模型复核：只在不确定或复杂事件时调用
  -> 提醒/记录/报告
```

这样能降低误报、降低 API 成本，也能更好解释“为什么提醒”。

成本控制规则要写进状态机，而不是只靠运营手动关接口：

1. 本地检测连续无人时，云端视觉进入暂停状态，只保留低频心跳复核。
2. 画面从无人变为有人、活动区域变化、任务状态变化时，立即触发一次云端视觉复核。
3. 画面稳定且没有提醒需求时，沿用上一状态，不重复调用大模型。
4. 安全事件、孩子主动求助、家长主动查看时，绕过省钱限制。
5. MiniMax VLM 只用于测评或特定复核场景，不作为每帧默认视觉入口。

### 9.4 隐私与合规

必须从第一版开始纳入：

| 领域 | 要求 |
|---|---|
| 监护人同意 | 收集、使用、上传儿童音视频前必须由监护人授权 |
| 数据最小化 | 默认只保存事件摘要和必要截图，不保存全天连续录像 |
| 本地优先 | 高频视觉检测、本地任务提醒尽量端侧完成 |
| 加密 | 传输 TLS，敏感数据本地加密和云端加密 |
| 对话记录 | 默认保存摘要，不默认长期保存所有逐字内容；安全事件例外 |
| 任务证据 | 只保存必要截图/短片和确认记录，不把所有行为长期留痕 |
| 成长时刻 | 默认精选和收藏，不保存全天录像，家庭成员分级可见 |
| 删除权 | 家长可删除照片、视频、对话摘要、逐字记录、报告、成长时刻和普通任务证据 |
| 访问控制 | 家庭成员分角色，避免非监护人查看 |
| 可见提示 | 录像、通话、远程查看时设备端有可见提示 |
| 第三方处理 | 调用大模型和推送服务前要有供应商评估和隐私告知 |
| 年龄边界 | 中国按不满 14 周岁儿童信息特殊保护，美国按 COPPA 13 岁以下儿童保护 |

## 10. MVP 范围与路线图

### 10.1 MVP 功能范围

第一版建议做得小而完整。MVP 内测可以使用第三方研发验证摄像头；正式商业版必须使用自有品牌 Mira Guardian（米拉）摄像头。

1. 家长 App 创建任务、任务模板和专注计时。
2. 摄像头按任务语音提醒。
3. 学习时坐姿提醒和离座提醒。
4. 孩子可用自己起的名字唤醒摄像头，进行普通短对话和题目引导式问答。
5. 家长可实时查看画面和发起音频通话。
6. 生成每日简报，并展示对话摘要、学习求助、任务证据、睡眠与安全关注点。
7. 记录奖励计量流水，支持孩子对摄像头说“我想换奖励”发起兑换申请，并由家长确认和兑现。
8. 支持 SOS 语音呼救、安全事件处理和紧急联系人推送。
9. 支持课程表/网课任务的手动录入、小书包、截图识别或日历导入，为后续学而思等平台合作预留接口。
10. 支持互动时长限制、免打扰和作业模式边界。

功能分级建议：

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | 任务证据、奖励兑换申请/兑现、睡眠基础卡片、安全事件处理、小书包、互动时长限制 | 直接增强家长端闭环，适合进入首版 MVP |
| P1 | 成长时刻、家庭协作、危险区域规则、睡眠趋势、作业依赖风险报告 | 有明显留存和信任价值，但需要更多样本与规则调优 |
| P2 | 孩子端 App、多孩多设备、长期成长档案导出、第三方学校平台自动提交 | 孩子端 App 用于奖励商店、申请状态和成长成就展示，仍需家长审核；其他能力价值高但复杂度、合规和外部依赖更高 |

暂缓：

1. 完整学习缺漏诊断。
2. 自动提交第三方学校打卡。
3. 高精度陌生人人脸库。
4. 多孩追踪。
5. 自有硬件量产。注意：这里的“暂缓”只代表不在软件 MVP 内完成量产，不代表商业版继续依赖第三方摄像头。
6. 未授权 IP 声包或直接模仿特定角色声音。
7. 长期成长档案导出。

## 11. 商业化建议

### 11.1 首发策略

首发不建议定位为“AI 教育硬件”或“学习机替代品”，否则会卷入题库、课程、教培内容竞争，也会被家长期待拉得过高。建议定位为：

> Mira Guardian（米拉）：覆盖安全、作息、陪伴、学习和家庭协作的儿童 AI 智护与成长中枢。

正式销售形态应该是：

```text
用户购买：Mira Guardian（米拉） AI 智护摄像头
用户下载：米拉家长 App
用户使用：App 配网绑定 → 设置孩子档案 → 设置任务/积分/安全规则 → 摄像头执行看护与陪伴
```

主卖点顺序：

1. 到点提醒和专注计时，减少家长反复催。
2. 任务模板，自动推荐小书包、作业、家务、打卡和睡前任务。
3. 家长远程查看和安全求助，覆盖孩子独自在家、家长突发状况等场景。
4. 作息、收纳、吃饭、睡前任务，帮助家庭建立规则。
5. 作业陪伴和坐姿提醒，减少鸡飞狗跳，但不把产品限制成学习机。
6. 每日/每周报告和积分激励，让家长看到成长过程，而不仅是学习成绩。
7. 教育内容生态入口，未来可与学而思网校等平台做课程任务、练习计划和联合会员合作。

### 11.2 定价建议

开发样机阶段不用急于定价。若未来自有硬件量产，可参考：

| 版本 | 建议 |
|---|---|
| 基础版 | 硬件 699-999 元，含基础提醒、实时查看、本地日报 |
| 订阅版 | 19-39 元/月，含云存储、高级报告、题目辅导额度、更多人设 |
| 家庭高级版 | 多设备、多孩子、多联系人、长期成长报告、合作内容包 |

注意：国内家长对订阅更敏感，基础功能必须足够有价值，不能让硬件买回去像“不开会员就废了”。

订阅页应放在“我的”中，而不是首页或任务主流程里强打扰。建议原型展示三层权益：基础版保留核心看护闭环；米拉会员提供云端长期报告、高级趋势、题目辅导额度和更多人设/声线；家庭高级版提供多设备、多孩子、多联系人、长期成长档案和合作内容包。付费页必须同时提供订单记录、续费状态、到期时间、取消/降级说明和权益用量，避免家长误以为基础安全能力需要额外付费。

### 11.3 硬件商业化原则

1. 不要求正式用户购买 TP-LINK、海雀、萤石等第三方摄像头。
2. 可以在内测阶段保留“兼容设备列表”，但只对自有品牌 Mira Guardian（米拉）硬件承诺完整体验。
3. 语音对话、隐私模式、端侧唤醒、OTA、App 配网、儿童数据删除都必须由自有硬件闭环负责。
4. 如果短期采用 ODM，品牌、App、固件策略、数据链路和用户体验仍应由米拉控制。

### 11.4 内容生态商业化原则

教育内容合作要服务产品主线，而不是把米拉变成另一个学习机商城。

1. 第一阶段先做任务流程入口：课程表、网课提醒、作业截图识别、练习计划卡。
2. 第二阶段谈授权集成：学而思网校等平台开放课程、作业、知识点和完成状态接口后，再做自动同步。
3. 第三阶段探索联合会员：米拉提供家庭场景监督和报告，内容方提供课程与练习。
4. 不复制第三方课程内容，不绕过对方账号和付费体系，不自动代孩子完成作业。
5. 内容推荐必须由家长确认，避免摄像头直接向孩子推销课程。

| 作业直接给答案 | 高 | Prompt、策略层、家长报告、限制答题模式 |
| 孩子沉迷聊天 | 高 | 时长上限、冷却、任务模式限制 |
| 对话记录造成被监控感 | 高 | 默认摘要、不默认逐字记录、可删除、记录模式可见提示 |

| 安全区域误报过多 | 中 | 支持敏感度、时段、区域大小和误报标记 |
| 第三方打卡无接口 | 中 | MVP 做素材采集，不做自动提交 |
| 大模型成本不可控 | 中 | 端侧预判、事件触发调用、无人暂停云端视觉、缓存和额度 |
| Kimi-K2.6 或 MiniMax 供应商限流/价格变化 | 中 | ModelRouter 抽象、按任务路由、保留本地固定话术降级 |
| MiniMax key 区域或接口不匹配 | 中 | 区分 `api.minimax.io` 国际站和 `api.minimaxi.com` 国内站，测评脚本支持配置 |
| Kimi API 不直接提供 ASR/TTS | 中 | 语音识别和语音合成独立成 SpeechGateway，TTS 可优先测 MiniMax Speech |
| MiniMax 文本接口不直接接收图片/音频 | 中 | 图片理解走 MiniMax VLM/understand_image，文本模型只做文本对话和报告 |
| 生成音乐和视频成本高 | 中 | 只做低频奖励/特殊场景，日常提醒使用 TTS 和预置音频 |
| 教育内容合作拿不到接口 | 中 | 先做手动录入、截图识别、日历导入和跳转，不把 MVP 绑定在合作上 |
| 未授权 IP 声音或形象侵权 | 高 | 只做原创声线/角色气质，商业声包必须授权 |
| 大厂跟进 | 中 | 先做家庭真实工作流和数据闭环 |

## 13. 立即行动清单

1. 移除 `server.py` 中 Demo 默认 API Key，全部改为环境变量。
2. 创建 `backend/` 模块化目录，把聊天、视觉、语音、报告拆出。
3. 采购并验证一台支持 RTSP/ONVIF 且双向音频能力可开放的云台摄像头，定位为研发验证机。
4. 新建 Flutter 项目，先做家长端首页、任务、任务详情和报告页的静态原型。
5. 设计任务/事件/积分/报告的数据库表。
6. 跑完 `evals/kimi_minimax/` 第一轮测评，用同一批图片、题目和日报事件比较 Kimi-K2.6、MiniMax-M2.7 和 MiniMax VLM。
7. 建立 `ModelRouter`：普通文本和日报优先 MiniMax，复杂视觉和安全复核按测评结果选择 Kimi 或 MiniMax VLM。
8. 为题目辅导写一版严格的“引导式而非答案式”Prompt，并配套自然话术库。
9. 把实时观察改成“本地预检 + 事件触发云端视觉 + 无人暂停云端调用”，避免 MiniMax VLM 或 Kimi 逐帧消耗。
10. 设计任务模板：上学日、周末、假期、考试周、睡前任务。
11. 设计小书包、睡眠基础卡片、任务证据、奖励商店和摄像头语音兑换申请的家长端原型。
12. 设计安全区域、成长时刻和家庭协作待办的 P1 原型，先控制权限和误报入口。
13. 为语音对话写防沉迷和互动边界策略：单次时长、每日总量、冷却期、任务模式、免打扰时段。
14. 设计原创童趣声线和外观方向，明确未授权 IP 不进入商用版本。
15. 设计对话记录策略：默认摘要、风险分级、家长可删除、逐字记录需明确开启。
16. 输出 Mira Guardian（米拉）自有摄像头硬件 PRD，包含麦克风、扬声器、NPU、隐私遮挡、OTA、配网、状态灯和自动播放能力。
17. 联系 2-3 家摄像头 ODM 或硬件伙伴，确认双向音频、端侧模型、固件开放度和小批量打样周期。
18. 做学而思网校等教育内容合作预研，先验证课程表/作业截图/跳转提醒/小书包能否形成高频使用。
19. 找 5 个目标家庭做访谈，重点验证任务模板、题目辅导、远程查看、安全告警、睡眠与奖励兑换的优先级。
20. 做 1 周家庭内测，只看三个指标：家长是否少催促、孩子是否愿意听、误报是否可接受。
